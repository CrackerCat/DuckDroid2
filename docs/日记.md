DuckEmu 设计文档 v1.0（收敛版）
这份文档是整个讨论的收敛结果。所有之前被指出错误、被修正、被降级为策略的内容，全部并入。它不再是"疯子版"，它是"收敛后的疯子版"——保留了疯的地方，但每一个疯的地方现在都有明确的边界和失败处理。

公理
不把 Guest 当成一个被模拟的进程，把它当成运行在宿主上的一个特权协程。

每份状态有且只有一个所有者，每个接口只暴露一件事，每个失败有且只有一个处理者。

共享运行时契约，不共享观测粒度。 Unicorn 和 Dynarmic 共享 SvcDispatcher、Memory 语义、Threads 语义、JNI Stub 行为；不共享指令级观测能力。

正确性不靠性能优化保证。 tlb_epoch 是优化，不是正确性来源；CodeWriteNotifier 是正确性来源。

隔离是策略，不是公理。 "一个签名器一个 WorkerProcess"是配置，不是硬编码。

三、System 层
3.1 职责
UDS 监听，HTTP/1.1 最小子集解析。

路由：(signer_profile_id, runtime_key) → WorkerProcess。

WorkerPool 管理：按配置 fork/health-check/restart/graceful-shutdown。

PrimordialProcess 维护。

System 不碰任何 Guest 内存、ExecutionBackend、JNI 状态。

3.2 路由语义
cpp
struct RouteKey {
std::string signer_profile_id;
std::string runtime_key; // hash(signer_id, so_set_hash, backend_type, config_rev)
};
亲和性：相同 runtime_key 优先路由到已加载该 RuntimeInstance 的 WorkerProcess；否则按 hash 选择 WorkerProcess。保证同一 key 落在同一进程。

3.3 PrimordialProcess 的语义
fork 模板里有：

已加载的 bionic 兼容层（libc 符号表、TLS 布局常量、errno 表）

已预热的 JnIStubRegistry（静态 JNI stub 已注册）

已加载的 libunicorn.so / libdynarmic.so 代码段（COW 共享）

SignerProfileConfig 只读快照

fork 模板里没有：

❌ 任何 uc_engine\* 实例（TCG 全局锁在 fork 后不一致）

❌ 任何 dynarmic::Jit 实例（JIT 编译器内部有线程相关全局状态）

❌ 任何 mmap 的 JIT 区（子进程需自己 mmap）

❌ 任何 RuntimeInstance

原因：fork 只复制调用线程，其他线程消失；Unicorn/Dynarmic 的全局状态在子进程是悬空的。WorkerProcess 在 fork 之后自己创建所有 ExecutionBackend 实例。

四、WorkerProcess 层
4.1 职责
RuntimeInstance 生命周期管理（创建、复用、销毁）。

HostThreadPool 调度。

MemoryPool 分区分配。

BackendFactory 创建 ExecutionBackend。

WorkerEventBus 上报。

WorkerProcess 不碰补环境语义。

4.2 隔离策略（降级为配置）
"一个签名器一个 WorkerProcess"不是公理，是策略。配置项：

cpp
struct WorkerProcessConfig {
IsolationMode mode; // ProcessPerSigner | SharedProcess
size_t warm_pool_size; // RuntimeInstance 预热数量
size_t max_runtime; // 最大并发 RuntimeInstance
BackendType backend; // Unicorn | Dynarmic
bool allow_reset; // 是否允许 warm pool 复用
};
ProcessPerSigner（默认，最安全）：崩溃/内存/JNI 隔离最好。

SharedProcess（可选）：多个签名器共享一个 WorkerProcess，用于资源受限场景。前提：签名注册表不冲突，so 不污染宿主全局状态（setenv/atexit/pthread_key_create）。

决定权在配置，不在架构。

4.3 两级调度
text
第一级：HostThreadPool（物理执行资源）
第二级：RuntimeThreadScheduler（逻辑执行单元，per-RuntimeInstance）
执行流程：

RuntimeThreadScheduler 的 futex_wake / clone 把 RuntimeThread 推入 RunnableQueue。

宿主线程从 RunnableQueue 取一个 RuntimeThread。

如果属于不同的 RuntimeInstance，切换 ExecutionBackend 上下文（Unicorn 换 uc_engine*；Dynarmic 换 Jit* + 刷新 TLB）。

宿主线程调用 instance.run_once(budget) 驱动执行，直到返回 RunResult。

根据 RunResult 决定：放回队列 / 归还宿主线程 / 通知请求处理器。

关键决策：ExecutionBackend 上下文切换有成本。亲和性优化（同一 RuntimeInstance 的 RuntimeThread 尽量在同一宿主线程跑）先不做，profile 后再加。

4.4 MemoryPool
WorkerProcess 启动时 mmap 一大段宿主虚拟地址（如 64GB，PROT_NONE），不提交物理页。按分区（每分区如 4GB）租给 RuntimeInstance 作为 Guest 地址空间的后备存储。

text
[MemoryPool] 宿主 VA: 0x7f_0000_0000 ~ 0x8f_0000_0000
│
├── Partition 0 → RuntimeInstance 1 的 Guest AddressSpace 后备
├── Partition 1 → RuntimeInstance 2 的 Guest AddressSpace 后备
└── ...
RuntimeInstance 销毁时：分区归还，物理页按配置保留（warm pool）或释放（分析模式）。

MemoryPool 不取代 Guest AddressSpace。物理后备复用不代表 Guest 虚拟地址和映射生命周期可以共享。

4.5 SharedReadOnlyPool
APK 字节、SO 字节、ELF 解析结果。

用 MAP_SHARED 或 COW 让多个 RuntimeInstance 共享不可变字节。

解码后的 Guest 映射（so 的 .text 段在 Guest VA 里的映射）仍是每个 RuntimeInstance 独立的。

五、RuntimeInstance 层：完整的 Android 补环境
5.1 定位
RuntimeInstance 就是 DuckEmu 的 Emulator。 补环境工程师拿到的就是这个对象，所有补环境操作都在它上面完成。

它是环境，不是容器。 Memory、Threads、Loader、VFS、Observer、Backend 都是它的成员，对补环境工程师不可见，只对 RuntimeInstance 自己可见。实现分散在模块文件里只是可维护性，不是"补环境工程师要去找 Loader 对象"。

5.2 对外门面
cpp
class RuntimeInstance {
public:
// —— 补环境的全部工作，直接在上面做 ——
ModuleHandle loadLibrary(const std::string& path);
FunctionHandle findSymbol(ModuleHandle, const std::string& name);

    Result callFunction(FunctionHandle, Args...);

    void  mem_write(GuestVA, const void*, size_t);
    void  mem_read(GuestVA, void*, size_t);
    void  mem_map(GuestVA, size_t, Permission);
    void  mem_unmap(GuestVA, size_t);
    void  mem_protect(GuestVA, size_t, Permission);

    uint64_t reg_read(RegId);
    void     reg_write(RegId, uint64_t);

    void add_hook(HookSpec);
    void add_trace(TraceSpec);

    RuntimeThreadId create_thread(std::function<void()> entry);
    void join(RuntimeThreadId);

    void register_native(ClassName, MethodName, Signature, Stub);

    // —— 对 WorkerProcess 可见 ——
    RunResult run_once(ExecutionBudget);
    void      reset();
    State     state() const;

private:
// 全状态所有者，实现分散在模块文件

};
这就是补环境工程师面对的全部接口。 不需要 getMemory()、getThreads()——直接 instance.mem_map()、instance.create_thread()。

```text

                  └──────────┘    └─────────┘
```

状态语义：

Executing → Suspended：阻塞 SVC（futex_wait 等），RuntimeThread 挂 WaitQueue，宿主线程归还。

Executing → Completed：请求完成。

Executing → Faulted：异常（非法指令、信号、未实现 SVC）。故障后不自动 Reset，必须先诊断。

Completed → Resetting → Ready：warm pool 复用。

Resetting 的硬约束：清空所有 RuntimeThread 寄存器、堆、.data 段、JNI 局部引用、pthread_once guard 状态。如果 so 注册了不能 reset 的全局状态，Reset 失败，标记 NonReusable，销毁。

超时：请求超时 → 只终止当前执行任务（backend\_->request_stop()），RuntimeInstance 进入 Faulted 或 Completed。不终止整个 RuntimeInstance，除非 Reset 失败。

分析模式：跳过 Resetting，Completed → Destroying → Destroyed。

六、关键子系统
6.1 ExecutionBackend：类型不可变，归 RuntimeInstance 所有
所有权：归 RuntimeInstance。理由：

Backend 实例不能 fork 继承（Unicorn TCG 锁 / Dynarmic JIT 线程状态悬空）。

Backend 上下文与 Guest AddressSpace 绑定，不能跨 RuntimeInstance 复用。

销毁必须与 RuntimeInstance 同步，否则 JIT cache 泄漏。

WorkerProcess 的角色：BackendFactory 按配置创建，交给 RuntimeInstance 持有。WorkerProcess 不直接持有 Backend 实例。

类型不可变：不能运行时切换 Unicorn ↔ Dynarmic。翻译缓存不兼容。

最小生命周期协议：

cpp
class ExecutionBackend {
public:
virtual ~ExecutionBackend() = default;

    virtual RunResult run(RuntimeThread& t, ExecutionBudget budget) = 0;
    virtual void request_stop() = 0;
    virtual BackendCapabilities capabilities() const = 0;
    virtual void invalidate_code(GuestVA addr, size_t len) = 0;

};
能力查询：告诉上层"我支持什么观测粒度"。上层代码必须能处理"我只拿到 block 级事件"这个现实。

6.2 执行预算（调度不能只在 SVC 边界）
cpp
struct ExecutionBudget {
uint64_t instruction_count; // 可选：Unicorn 精确，Dynarmic 近似
uint64_t wall_clock_ns; // 必选：两者都能实现
uint32_t block_count; // 可选：按基本块
};

enum class RunResult {
Completed, // 正常返回
SvcPending, // 遇到需分发的 SVC
BudgetExhausted, // 预算用尽，需调度
Exception, // 异常
};
Unicorn：指令计数中断（uc_ctl）或宿主定时器。

Dynarmic：宿主定时器 + 每 N 个 block 检查。

调度器不假设让出点。 每段执行在预算耗尽时返回 BudgetExhausted，由 RuntimeThreadScheduler 决定是否切换。SVC 只是额外的、更友好的让出点。

6.3 Memory：Guest 地址空间唯一权威
Memory 负责 Guest 虚拟地址空间的映射、权限、归属。不拥有 Dynarmic JIT cache。

Guest 代码页 vs Dynarmic JIT 缓存：两种地址空间坐标，不是同一张页表的两个视图。把 Guest 的 mprotect 直接作用在宿主 JIT 页上是错的——Guest 根本不应该看见、也不能 mprotect 到 Dynarmic 的 JIT 区。

正确的代码修改协议：

cpp
class CodeWriteNotifier {
void notify_write(GuestVA addr, size_t len);
};
写代码页 → Memory 完成写入 → 调 notify_write(addr, len)

Unicorn 后端：对受影响的 Guest VA 调 uc_ctl(UC_CTL_TB_REMOVE_CACHE)

Dynarmic 后端：查"已翻译 VA 区间 → block 列表"索引，逐 block 清并重编

mprotect 数据页 → 可执行页：视为代码页变化

tlb_epoch 降级为性能优化提示，不是正确性保证。正确性由 notify_write 保证。

不靠单一版本号解决 SMC：跨页基本块、块链接、后端绕过 Memory 写入路径，tlb_epoch 兜不住。必须定义完整的 CodeWriteNotifier 协议。

6.4 Threads：futex 驱动的调度器
clone 和 futex 是同一个东西的两面，都操作 WaitQueue。

cpp
struct RuntimeThread {
uint64_t tls_tp;
uint64_t stack_base;
uint64_t pc, sp, regs[31];
FutexWaitQueue\* waiting_on;
uint64_t clear_child_tid;
};
clone：从池取空闲 RuntimeThread，设 tls_tp（指向该线程的 bionic TCB），记录 child_tid，标 runnable，推 RunnableQueue。

futex(FUTEX_WAIT)：若 \*uaddr == val，当前线程挂 WaitQueue，切换。

futex(FUTEX_WAKE)：从 WaitQueue 摘 N 个线程，标 runnable，推回队列。

join 语义：子线程退出时检查 clear_child_tid != 0，向该地址写 0，futex_wake(1)。父线程被唤醒，pthread_join 返回。

clone、futex、exit、clear_child_tid 分别建模，不能靠一个 WaitQueue 替代完整线程生命周期。

Backend 不被任何线程拥有；任意时刻只被一个 RuntimeThread 驾驶，驾驶权由调度器在 SVC 边界或预算耗尽时移交。

6.5 TLS：真实 bionic ABI，不是硬编码示意
TCB 布局：按目标 Android 版本（如 Android 12/13/14）的 bionic pthread_internal_t / bionic_tls 实际结构体抄，从 bionic 源码来。

静态 TLS：ELF PT_TLS 段，按 TLS variant 规则（ARM64 是 variant 1，x86_64 是 variant 2）摆放。

动态 TLS：\_\_tls_get_addr 的 DTV 更新，按 dl_tls_dtv_slotinfo_list 语义走。

每线程实例化：RuntimeThread 创建时，Threads 层从 TLS Manager 请求"分配一个 TLS 实例"，布局和大小由模块注册阶段决定。

按版本分文件，测试用例覆盖每个字段的读写。别再写示意性的字节偏移。

TLS 是 per-RuntimeThread 的，不是 per-module 的全局变量。 Loader 加载 so 时遇到 PT_TLS 不自己 mmap，而是调 Threads::allocate_tls_for_module(module)，为每个活跃 RuntimeThread 的 TLS 实例扩展偏移并更新 DTV。

6.6 Loader：TLS-first
读 ELF header，遇到 PT_TLS 立即调 Threads::allocate_tls_for_module()。

解析 DT_NEEDED，递归加载依赖。

处理重定位：R_AARCH64_RELATIVE、GLOB_DAT、JUMP_SLOT。

符号解析顺序：全局 scope → 模块自身 → RTLD_DEFAULT → RTLD_NEXT（与 bionic linker 一致）。

VFS 只是 open/read/mmap 的文件后端。loader 跑通前，VFS 只需从宿主文件系统读 ELF。

6.7 Observer：语义事件同步，诊断事件异步
Backend 不调用 Observer。Backend 写入无锁环形缓冲区，Observer 异步消费。 但语义事件必须同步可靠报告，因为调度器和状态机依赖它们。

cpp
// 语义事件：同步可靠通道
SvcEvent(imm, args, ret)
ModuleLoaded(path, base, size)
MemoryMapped(va, size, perm)
ThreadCreated(tid, tls_tp)
ThreadSwitched(from, to, reason)

// 诊断事件：异步可丢环形缓冲
InsnSnapshot(pc, regs[31])
MemAccess(addr, size, rw)
BlockEnter(pc, size, core_id)
语义事件同步可靠（可能在 SVC 边界直接调用），诊断事件异步可丢（消费者慢则丢，必须能识别日志丢失）。

不要把 MemReadAfter 这种 Unicorn 专有粒度泄露到 Observer 公共接口。

6.8 JNI：ABI 一次性适配，语义靠注册表
JNI ABI 是固定契约：ARM64 上 JNIEnv\* 走 x0，jobject 走 x1，其余按类型规则走 x2~x7 / 栈。一次性 ABI 适配层，不是每个函数一份：

cpp
template<typename Ret, typename... Args>
Ret invoke_jni_stub(fn_ptr, JNIEnv\* env, jobject thiz, Args... args);
三路匹配：

RegisterNatives 实际注册记录（最强证据）：拦截 RegisterNatives JNI 函数调用入口（不是 Linux SVC），把 {name, sig, fnPtr} 录下来。

导出符号名（强证据）：Java_com_example_Foo_bar\_\_Ljava_lang_String_2 → 类、方法、签名。

调用栈弱证据：前两路都没命中时，Guest 在 Java stub 侧最近一次 Call\*Method 的签名作为弱证据。

签名决定 ABI，名称/注册表决定语义。 签名匹配只作为语义层的兜底，不承担 ABI 职责。

Stub 用注册表替代 switch：

cpp
REGISTER_STUB("java/lang/String", "hashCode", "()I",
[](JNIEnv\* env, jobject thiz) -> jint {
auto s = env->from_jstring(thiz);
return std::hash<std::string>{}(s);
});
JNI Stub 区分通用 JNI 语义（复用 JNI Runtime）与目标应用具体行为（注册表关联）。

6.9 关于嵌入真 JVM：不要。至少第一版不要。
嵌入 JVM 面对：两个 GC、两个线程模型、JNI 局部引用生命周期悬空。用 JavaMethodStub DSL（C++ lambda 填满 JNIEnv 函数表）替代，生命周期由 RuntimeInstance 控制，轻 100 倍。

真的需要跑复杂 Java 逻辑（壳在 Java 层做校验）时再考虑嵌入，那时你已经有足够的调试基础设施判断边界。

  └── PrimordialProcess (fork 模板)

WorkerProcess          │

实现顺序（必须最先跑通什么）
RuntimeMemoryManager + TLS 实例化。按真实 bionic 源码硬编码 TCB 布局。

clone + CLONE_SETTLS + CLONE_CHILD_CLEARTID + futex WAIT/WAKE。

八、核心不变量（每一条都必须被测试覆盖）
每份状态有且只有一个所有者。Guest 内存归 RuntimeMemoryManager；RuntimeThread 归 RuntimeThreadScheduler；JIT cache 归 ExecutionBackend；APK 字节归 SharedReadOnlyPool。

每个接口只暴露一件事。instance.mem_map() 只做映射，不做 TLS 分配；instance.loadLibrary() 只加载，不跑业务逻辑。

每个失败有且只有一个处理者。RunResult::Exception 由 RuntimeInstance 状态机处理（→ Faulted），不由 WorkerProcess 猜。

语义事件同步可靠，诊断事件异步可丢。

SMC 正确性由 CodeWriteNotifier 保证，不靠 tlb_epoch。

调度不只在 SVC 边界，靠 ExecutionBudget。

TLS 布局来自真实 bionic 源码，不硬编码示意。

JNI ABI 一次性适配，语义靠 RegisterNatives + 导出名，签名匹配兜底。

warm pool 复用前提是 Reset 语义可满足；Reset 失败即弃用。

隔离是策略，不是公理。"一签名器一 WorkerProcess"由配置决定。

九、一句话总结
RuntimeInstance 就是 DuckEmu 的 Emulator。 补环境工程师拿到的就是这个对象，所有补环境操作都在它上面完成；Memory、Threads、Loader、VFS、Observer、Backend 都是它的成员，对工程师不可见。

先让 tpidr_el0 读到正确的值。先让 pthread_join 返回 0。先让 Ready → Executing → Completed → Resetting → Ready 跑通。

其余的，都是在这三块石头上长出来的。
