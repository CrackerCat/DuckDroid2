# 属性区：让真 libc 自己读 /dev/__properties__

> 日期：2026-10-30
> 审计 1（属性层）的收尾；真机取值来自已连接的小米 8（dipper，SDK 32）。

## 1. 结论先说

属性不走符号 interpose，也不在 runtime 里做一张 `name -> value` 表。
runtime 只生成 Android 14 init 会写出的 **三份二进制文件**
（`property_info`、`properties_serial`、`u:object_r:<ctx>:s0`），通过 VFS 暴露在
`/dev/__properties__/` 下；libc 自己的 `__system_properties_init` 在 preinit
里解析它们。之后 `__system_property_get/find/read_callback/foreach` 全部是
真 bionic 代码在跑，runtime 不参与。

这样做的直接好处：

- 不需要为每个 API（get / find / read / read_callback / foreach / serial /
  wait）各写一个 thunk，也不会漏掉 libc 内部对自己的调用。
- 属性区的 trie、脏备份区、long-property（>92 字节）语义与真机一致；
  `read_callback` 拿到的 `prop_info*`、serial 都是真的。
- 以后要加值只改数据（DeviceProfile 或 property 文件），不改代码。

## 2. 源码依据（本机 ROM = LineageOS 21 / Android 14 / lemonade）

| 位置 | 事实 |
|---|---|
| `bionic/libc/bionic/libc_init_dynamic.cpp` | `__libc_preinit` 是 constructor(1)，里面调 `__libc_init_common` |
| `bionic/libc/bionic/libc_init_common.cpp:171` | `__system_properties_init()` 就在 `__libc_init_common` 里 |
| `bionic/libc/bionic/system_property_api.cpp` | 所有 `__system_property_*` 都是对 `SystemProperties` 的转发 |
| `bionic/libc/system_properties/system_properties.cpp` | `Init(PROP_DIRNAME)`；目录存在且 `access("/dev/__properties__/property_info", R_OK)==0` 时走 `ContextsSerialized` |
| `bionic/libc/system_properties/contexts_serialized.cpp` | 依次加载 `property_info`、`properties_serial`，再按名字取 `u:object_r:<ctx>:s0` |
| `bionic/libc/system_properties/prop_area.cpp` | Android 13/14 的 **trie** 布局；128 KiB、magic `0x504f5250`、version `0xfc6ed0ab`；`map_fd_ro` 要求 stat uid/gid==0 且 size ≥ 128 |
| `bionic/libc/system_properties/prop_info.cpp` | `prop_info{serial, value[92], name}`；serial = `valuelen<<24`；长值用 `kLongFlag=1<<16` + 相对偏移 |
| `system/core/property_service/libpropertyinfoparser` | `property_info` 的序列化 trie 格式与 `CheckPrefixMatch` 语义 |

两个关键事实决定了实现方式：

1. **运行时不需要额外调用 libc**：`__libc_preinit` 已经在我们加载 libc 时执行
   （M4.6 的 `04c_preinit` 就是在验证这一点），`__system_properties_init` 自然
   被带上。VFS 在 `create()` 时就已经就绪，所以只要文件在，init 就会成功。
2. **`prop_area` 是纯数据**：`find()` 只在文件镜像上走 trie，不做任何写操作；
   guest 侧 `MAP_SHARED|PROT_READ` 的 mmap 由现有 `sysMmap` 拷贝填充即可。

## 3. 镜像格式（只列实现依赖的部分）

### 3.1 `prop_area`（每 128 KiB）

```text
0x000  uint32 bytes_used          // data_ 内已用字节
0x004  uint32 serial
0x008  uint32 magic = 0x504f5250
0x00c  uint32 version = 0xfc6ed0ab
0x010  uint32 reserved[28]
0x080  data_[0]
```

`data_` 从 0 开始是根 `prop_trie_node`（namelen/prop/left/right/children/name，
20 字节，初始全 0），紧跟着 92 字节 dirty backup，所以第一个分配偏移是
`20 + 92 = 112`。之后每个 `prop_trie_node` 按 token（'.' 分段）挂成
「子节点树的二叉搜索树」，比较规则与源码 `cmp_prop_name` 一致：先比长度，
再比字节。`prop_info` 是 96 字节头 + name，长短值两种形式都与
`prop_info.cpp` 对齐。

### 3.2 `property_info`

头部 6 个 uint32（版本、size、contexts/types 偏移、root 偏移），随后是
context 字符串数组、type 数组和 trie。本实现把所有属性放进一个
context（`u:object_r:default_prop:s0`），根节点只放一条 **长度为 0 的 prefix
entry**：`CheckPrefixMatch` 对任何 remaining name 都会命中，于是所有名字都解析到
context 0。格式本身保留 prefix 数组，未来要按真实 `property_contexts` 拆 context
时只改数据。

### 3.3 长值

值 ≥ 92 字节时按 bionic 的 long-property 形式写入：serial 的高字节存
legacy 错误信息长度并置 `1<<16`，`prop_info` 的 value 区放错误文案，偏移字段
指向后面的真值。`__system_property_get` 对这种属性返回的是错误文案（与真机
一致），只有 `read_callback` 能拿到全文。

## 4. 实现

| 文件 | 职责 |
|---|---|
| `runtime/props/property_table.*` | 设备身份属性（由 `DeviceProfile` 派生）+ `name=value` 文件覆盖层 |
| `runtime/props/property_image.*` | 生成 `prop_area` trie / 序列化 `property_info` / serial 区 |
| `runtime/props/property_files.*` | 把三份镜像挂成 `/dev/__properties__` 下的 0444 文件 |
| `runtime/vfs/synthetic_file_system.hpp` | 新的只读合成挂载接口（`/dev` 节点的下一站） |
| `runtime/vfs/file.*` | `StaticFile`：不可变内容、root 属主、0444 |
| `runtime/vfs/virtual_file_system.*` | open/stat/access 先查合成挂载；`statFd` 对 `systemOwned()` 文件跳过设备 uid 覆盖 |
| `runtime/instance/runtime_instance.*` | `RuntimeConfig::property_file`；`create()` 建镜像并把指针交给 VFS |
| worker / system | `--property-file PATH`（worker）与 `property-file=PATH`（`--app` 串） |

身份耦合仍然只有一处来源：`ro.product.*`、`ro.build.fingerprint`、
`ro.build.version.*`、`ro.debuggable`、`ro.secure`、ABI 列表、`ro.sf.lcd_density`
都由 `DeviceProfile` 派生，`ro.build.id` 从 fingerprint 里解析。文件只做覆盖，
所以 `uname`、`getuid`、`/proc`、`stat` 和属性永远说同一套话。

写路径不存在：property service 没有建模，`open(..., O_WRONLY)` 返回 EROFS。

## 5. 测试

`04i_properties`：加载 ROM libc（preinit 触发属性 init），然后用 libc 自己的
出口验证：

- `__system_property_area_serial()` 不是 `0xffffffff`（初始化成功的证据）；
- `__system_property_get`：派生值、文件覆盖值、空值、不存在的键（返回 0 且清空）；
- `__system_property_find` 对存在/不存在一致；
- `__system_property_read_callback`：普通值与 100 字节长值（serial 带
  `kLongFlag`，值完整）；
- `__system_property_foreach`：host thunk 通过 `call_guest` 回调
  `__system_property_read`，能看到全部条目。

全量 **40/40**。

## 6. 真机数据与一个真实发现

小米 8 的 `getprop` 转成 build.prop 语法（去掉 `cache_key.*` 与含换行的
`persist.sys.boot.reason.history`），成为 `code/user_code/jdgs_case/jdgs.properties`
（504 条），作为 JD 包的**设备画像**。

这条数据立刻暴露了一个目标侧事实：**京东 16.1.50 的签名器在
`ro.build.version.sdk >= 33` 时走进另一条平台路径并返回 -4210**（22–32 全部
正常）。默认 `DeviceProfile` 是 SDK 33，所以属性层一开，JD 门禁就从"空属性"变成
"属性说 33"——两者对目标都是新输入。

结论不是去改默认值，而是确认分工：**设备画像是目标包的数据**。JD 包携带它被
验证过的 Mi 8 画像，worker 用 `property-file=` 传入。这也是这套设计的意义：
以后接新目标/新机型只加一个数据文件。

## 7. 仍未覆盖

- 多 context 拆分：目前全量进 `default_prop`；`property_info` 已按 prefix 表构造，
  真 `property_contexts` 可以后续灌进来。
- SELinux 访问控制不建模（`access(2)` 对属性文件恒可读）。
- 属性写入 / property service socket（`__system_property_set` 仍走真机的
  `/dev/socket/property_service`，当前没有该 socket）。
- 缺口审计 A 组里 `ioctl(54)` 明确不做（TTY/管道的 ioctl 语义无法可靠覆盖），
  其余项按列表继续。
- `ro.build.date`、`ro.build.version.security_patch` 等 `DeviceProfile` 没有的
  字段由数据文件提供。
