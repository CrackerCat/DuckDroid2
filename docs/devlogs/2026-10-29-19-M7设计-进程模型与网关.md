# 2026-10-29 M7 设计：进程模型、调度与 UDS 网关

> 前置：
> - `docs/里程碑.md` M7
> - `docs/日记.md` §3.3（PrimordialProcess 语义：fork 模板不得含 engine / 实例）
> - `docs/目录说明.md` §七/§八（system / worker / protocol 的意图）
> - DuckDroid `code/product/{system,worker,protocol}`（同构参考，差异见 §11）
>
> 本轮拍板（2026-10-29）：
> 1. **System 是小网关**：UDS 接上层 Web API，把签名参数交给 WorkerProcess，
>    结果逐级原样返回。
> 2. **WorkerProcess 按项目划分**（京东 / 快手 / 抖音 / …），一个项目一个 Worker。
> 3. **RuntimeInstance 是进程**：Worker fork 子进程，每个子进程在 fork 之后
>    自己 `RuntimeInstance::create`；实例进程是并发单位。
> 4. **M6 剩余项并入 M7**：与 DuckDroid 的 1..100 逐值对拍、warm pool reset。

---

## 0. 一句话模型

```
Web API ──UDS──> System ──socketpair──> Worker(项目) ──socketpair──> Instance 子进程
                （网关/监督）           （supervisor/调度）        （RuntimeInstance，并发单位）
```

签名方向：请求逐级下传；结果逐级上抛。任何一层崩了，由它的父进程负责发现和重启。

---

## 1. 进程拓扑与职责

| 进程 | 个数 | 职责 | 明确不做 |
|---|---|---|---|
| **System** | 1 | 每项目一个 UDS listener；accept；按项目选 Worker；转发帧；监督 Worker（等待/重启/优雅退出） | 不解析请求体；不碰 guest 内存、engine、JNI |
| **Worker** | 每项目 1 个（`workers=N` 时为 N 个） | 拥有实例池与调度；fork/reap 实例进程；会话表；超时、回收、预热 | 不创建 RuntimeInstance；不碰 engine |
| **Instance** | 每 Worker `instances` 个 | 在 fork 之后 `RuntimeInstance::create`，执行 init 与 invoke；一个实例一次只处理一个请求 | 不 accept 客户端；不认识 UDS / 项目路由 |

进程命名（`prctl(PR_SET_NAME)`，测试与运维靠它找进程）：

```
duckemu-system
duckemu-worker:<app>
duckemu-inst:<app>:<n>
```

## 2. 为什么实例只能在 fork 之后创建

用户提出的另一种形态是：Worker 先开一个 RuntimeInstance，再从这个 RuntimeInstance
fork 出多个实例。**本设计明确否决**，理由是源码级事实：

1. `RuntimeInstance` 一创建就带宿主线程：`scheduler.cpp:101` 为 guest 主线程起一个
   `std::thread`，`scheduler.cpp:702` 为每个 guest 线程再起一个。
2. `fork()` 只复制调用线程；子进程里其他线程消失，`std::thread` 对象、条件变量、
   futex 等待队列、`execution_mutex` 的持有者全部悬空。
3. Unicorn 的 TCG 状态、代码缓存与锁是进程内全局状态，fork 后不一致
   （`docs/日记.md` §3.3 已写成规则）。

**规则**：Worker 永不创建 RuntimeInstance；fork 点必须早于任何 engine / 宿主线程。
想在 fork 之间共享初始化成果，只有一条合法路径：fork 模板里只放**只读数据**
（ROM 的 `.so` 映射、ELF 解析结果、符号表），不放 engine、不放实例。这就是
PrimordialProcess；v1 不做（见 §11），先把正确性做出来。

实例创建的真实代价（libeleven）：cold start ≈ 1.5 s（M6 实测）。摊薄手段是
**warm pool**，不是 fork 活实例。

## 3. 实例数量与并发

- 配置里的 `instances = N` 是**并发上限**：N 个实例进程，最多 N 个请求同时在 guest 里跑。
- `prewarm = P ≤ N`：保持 P 个已 init 的空闲实例；新会话优先拿 warm 实例，
  避免请求路径上等 init。**v1 实现取 `P = N`**：启动时把 `instances` 个实例
  全部拉起并预热，按需扩容（P < N）延后。
- 一个实例同一时刻只处理一个请求（实例内并发来自 guest 自己的线程，不是跨请求复用）。
- 实例进程之间存在会话亲和：`session` 绑定的实例未死之前，该会话的请求都去同一实例。

冷启动、预热、排队的关系：

```
请求到达
  ├─ 有 session 且在表里 → 该实例（忙则入该实例队列，深度受限）
  └─ 无 session
       ├─ 有空闲实例 → 分配，登记会话
       ├─ 未到 N → spawn 新实例，请求进入 warm 等待（≤ prewarm_wait_ms）
       └─ 已到 N 且无空闲 → 全局排队（≤ max_pending_requests），否则 OVERLOADED
```

## 4. 协议

### 4.1 外部：Web API ↔ System

- 每个项目一个 UDS 路径：`<socket_dir>/<app>.sock`。**连接本身决定 app**，
  System 因此不需要解析 JSON。
- 帧：4 字节大端长度 + UTF-8 JSON 包体（与 DuckDroid 一致，Python 端零成本）。
- 一个连接可发多个请求；同一连接上的响应按请求顺序返回。

请求（客户端 → System）：

```json
{
  "version": 1,
  "id": "req-0001",              // 客户端生成，响应原样带回
  "op": "sign",
  "session": {"id": "...", "seed": 0},   // 可选；seed 非 0 时实例随机流可复现
  "params": {"value": "1"},               // 项目自定义键值
  "deadline_ms": 5000                     // 可选
}
```

响应（System → 客户端）：

```json
{
  "version": 1,
  "id": "req-0001",
  "app": "libeleven",
  "worker": "w-<uuid>",
  "instance": "i-<uuid>",
  "ok": true,
  "result": {"value": "1:1792886400000"},
  "error": {"code": "...", "message": "...", "stage": "invoke",
            "retryable": false, "new_session": false},
  "meta": {"queue_us": 12, "init_us": 0, "invoke_us": 1432,
           "instance_requests": 3, "recycled": false}
}
```

错误码沿用 DuckDroid 的集合（`BAD_FRAME` / `BAD_JSON` / `UNKNOWN_OP` /
`SESSION_NOT_FOUND` / `SESSION_GONE` / `OVERLOADED` / `INITIALIZING` /
`QUEUE_TIMEOUT` / `DEADLINE_EXCEEDED` / `CALL_TIMEOUT` / `GUEST_FAULT` /
`INIT_FAILED` / `INTERNAL`），中文文档不重复展开。

### 4.2 内部：System ↔ Worker

socketpair，System 转发**不透明帧**，只加连接标识：

```
[4B conn_id][4B frame_len][frame bytes]
```

- 请求与响应同一套信封；Worker 回包的 `conn_id` 由 System 映射回客户端 fd。
- System 不看 `frame bytes` 的内容；worker 崩溃时 System 用 `conn_id` 找到
  正在等这个 worker 的连接并回错误。

### 4.3 Worker ↔ Instance

同构帧（4B 长度 + JSON），消息类型由 `type` 字段区分：

| type | 方向 | 载荷 |
|---|---|---|
| `init` | Worker → Instance | app id、library 路径、clock 注入基值、会话 seed |
| `ready` | Instance → Worker | instance uuid、init_us |
| `init_failed` | Instance → Worker | code、message |
| `invoke` | Worker → Instance | 原始请求的 `id`/`op`/`params`/`deadline_ms` + 会话 uuid |
| `result` | Instance → Worker | ok/result/error + invoke_us、实例内已服务请求数 |
| `shutdown` | Worker → Instance | 排空后退出（drain） |

实例进程启动后**先建 RuntimeInstance 再 `ready`**，不做请求路径上的懒加载
（懒加载只保留给测试；生产靠 prewarm）。

## 5. 调度与故障

### 5.1 实例状态机

```
Starting ──ready──> Ready ──dispatch──> Busy ──result──> Ready
   │                  │                                    │
   └─init_failed─> Dead <──kill/timeout/crash/recycle──────┘
```

### 5.2 规则

- 会话表：`uuid → instance`。实例死亡/回收即删除绑定；之后带该 session 的请求回
  `SESSION_NOT_FOUND` + `new_session=true`（绑定尚存、实例已替换的竞态回
  `SESSION_GONE`）；客户端去掉 session 重试。
- 队列上限：每实例 `session_queue_depth`，全局 `max_pending_requests`；
  超限直接 `OVERLOADED`，不无限堆积。
- 超时：Worker 计时，超时即 `SIGKILL` 实例进程并回 `CALL_TIMEOUT`
  ——这是唯一可靠的 guest 超时（M3 已证明 Unicorn 自带 timeout 有竞态）。
- 回收：`max_requests_per_instance`（可选）、`host_recycle_bytes`、Worker 级
  `rss_budget_mb`。回收 = 让实例退出并补一个新实例，**没有 in-place reset**。
- 崩溃：`SIGCHLD` + `waitpid` 发现；在途请求回 `GUEST_FAULT`；
  补实例带 backoff；连续失败超过 `max_consecutive_failures` 时该槽位标记 down，
  不再热重启。
- Worker 崩溃：System 发现 socketpair EOF / `waitpid`，回在途请求错误，
  backoff 后 `posix_spawn` 新 Worker；客户端连接不要求断开重连（v1 尽力而为）。

### 5.3 与 M6 的 reset 语义对齐

M6 的 `06_warm_pool_reset` 要求「reset 后第二个请求结果一致」。进程模型下
reset 就是**换实例进程**：

- 两个请求使用同一注入时钟基值（确定性时钟），
- 第 1 个请求后实例被回收，第 2 个请求落在新实例（`instance` UUID 不同），
- 两个 `result` 必须逐字节相同。

## 6. 生命周期与 fork 卫生

- **System → Worker**：`posix_spawn`（`--worker-exec` 指向 worker 二进制），
  socketpair 通过 fd 继承（清除 `FD_CLOEXEC` 后 exec）。System 是多线程的
  （accept / 每连接 / monitor），所以不用裸 `fork`。
- **Worker → Instance**：`posix_spawn` 自身（`duckemu_worker --instance ...`），
  socketpair 的子端在 file actions 里 `dup2` 到固定 fd 3。理由：exec 之后
  fd 表、内存、锁状态全干净，engine 一定在 exec 之后创建；进程命名也清楚；
  配置经 argv 重新传入，不依赖继承的内存。
- **Worker 的线程模型**：supervisor 不建 engine，但**每个实例槽位配一个 I/O 线程**
  （只搬帧：发 `invoke`、收 `result`、处理超时与子进程死亡）。主线程只读
  System 通道并按槽位排队。这样请求并发由线程数 = 实例数决定，阻塞 I/O 不需要
  epoll 状态机；supervisor 里没有任何 Unicorn 状态，`posix_spawn` 仍是线程安全的。
- **fd 卫生**：除显式传递的 fd 外全部 `FD_CLOEXEC`；Worker 不继承 listener
  （listener 在 System）；Instance 不继承 Worker 的任何客户端 fd。
- **就绪**：Instance 完成 init 后发 `ready`；Worker 收到后才计入 warm 池。
  System 等 Worker 的首个业务握手（v1 用 socketpair 上的一条 hello）才开始接客。
- **信号**：System/Worker 用 `signalfd` 处理 `SIGCHLD`/`SIGTERM`/`SIGINT`；
  `SIGPIPE` 忽略。
- **优雅退出**：System 停 accept → 通知 Worker drain → Worker 等在途请求
  （≤ `shutdown_grace_ms`）→ 通知实例 `shutdown` → 超时 `SIGKILL` 剩余进程。

## 7. 目录与模块

```
code/src/common/uds/            # Socket 封装（listen/connect/accept/read/write/fd 继承）
code/src/protocol/
├── frame.{hpp,cpp}             # 4B 长度帧读写
├── messages.{hpp,cpp}          # Request/Response/ErrorInfo/Meta + JSON 编解码
└── routing.{hpp,cpp}           # app → socket 路径；Worker 选择（v1: 轮询健康槽位）
code/src/system/
├── main.cpp
├── system.{hpp,cpp}            # 生命周期、连接线程、reap
├── uds_frontend/               # 监听与 accept
├── router/                     # 按 listener/app 选 Worker
├── worker_pool/                # spawn / monitor / respawn / 转发 / 在途请求失败
└── config/                     # app 列表（id、bundle、library、workers、instances…）
code/src/worker/
├── main.cpp                    # 两种模式：supervisor / --instance
├── worker_process.{hpp,cpp}    # 池、调度、会话表、超时、回收、SIGCHLD
├── instance_host.{hpp,cpp}     # --instance 模式：RuntimeInstance 的 init/invoke 循环
└── app/                        # AppPlugin 接口（target-agnostic）
code/user_code/libeleven_case/  # 项目侧：plugin.cpp（Java 环境 + 加载 + invoke）
```

硬边界（沿用 `目录说明.md`）：`src/system/` 不 include 任何 `runtime/` 头；
`src/worker/app/` 不认识具体项目，具体项目在 `user_code/` 注册。

### 7.1 AppPlugin（Worker 侧唯一的目标接缝）

```cpp
class AppPlugin {
 public:
  virtual ~AppPlugin() = default;
  // Init: installJavaEnvironment + loadLibrary(libc) + loadLibrary(target)
  virtual bool init(runtime::RuntimeInstance &rt, std::string *error) = 0;
  // Invoke: params → guest 调用 → result；不得改变模块/环境集合
  virtual bool invoke(runtime::RuntimeInstance &rt,
                      const protocol::Request &req,
                      protocol::Result *out, std::string *error) = 0;
};
using AppPluginFactory = std::function<std::unique_ptr<AppPlugin>()>;
```

注册表在 `code/user_code/registry.cpp`（target 侧），Worker 按 app id 取工厂。
libeleven 的 plugin 直接复用现成的 `libeleven_case` 环境与调用序列。

## 8. 配置（v1）

v1 用命令行，够跑 gate；配置文件（JSON/YAML）随后：

```
duckemu_system --socket-dir /tmp/duckemu --worker-exec ./duckemu_worker \
  --app id=libeleven,library=/path/libeleven.so,workers=1,instances=4,prewarm=2 \
  --wall-time-ns 1792886400000000000 --trace DIR
```

可重复 `--app`；每个 app 一个 socket、一个 Worker 池。Warm pool / 队列 /
超时 / 回收参数都挂在 app 上（默认值取 DuckDroid 的量级）。

## 10. Gate `07_end_to_end`

一个测试文件，起真实二进制（System + Worker + Instance），不 mock：

1. **单请求**：连 `libeleven.sock`，`value=1`，结果等于进程内直跑的 `data(1)`。
2. **并发**：8 个客户端各发 25 个请求（`value` 1..100 交错），全部正确；
   `meta.instance` 出现多个实例，且总耗时明显低于串行。
3. **实例崩溃**：kill 一个 `duckemu-inst:*` 进程；在途请求得到
   `GUEST_FAULT`/`CALL_TIMEOUT`，随后的请求在新实例上成功，会话收到
   `SESSION_GONE` 或自动换新实例（按设计）。
4. **Worker 崩溃**：kill 一个 `duckemu-worker:*`；System 在 backoff 后拉起，
   新请求成功；旧连接拿到可重试错误。
5. **回收/reset**：`max_requests_per_instance=1`，两次请求结果一致、
   `meta.instance` 不同。
6. **对拍**：`1..100` 与 DuckDroid 参考输出一致。

## 11. 不做 / 延后（与路线图的偏差）

| 项 | 处理 | 原因 |
|---|---|---|
| HTTP/1.1 解析 | 不做 | 上游 Python 负责（路线图原定） |
| MemoryPool（宿主 VA 分区租约） | 延后 | 实例已是独立进程，VA 天然隔离；跨进程分区没有收益 |
| PrimordialProcess 预载 | 延后 | 只对「fork 前只读预载」成立，需要 loader 配合；v1 用 warm pool |
| 跨 Worker 会话路由 | v1 不做 | 默认每 app 1 个 Worker；多 Worker 时会话绑定到连接，重连可能 `SESSION_NOT_FOUND` + `new_session` |
| 动态扩缩容 / 全局负载均衡 | 延后 | 先固定 N |
| Dynarmic | 独立里程碑 | 路线图原定 |
| Worker ↔ System 管理面（状态查询） | v1 只做 hello + 退出 | 测试靠进程名与 `/proc` |

**路线图 M7 交付物随之修订**：`src/worker/` 里的 MemoryPool 与
`src/system/primordial/` 降为延后项，不再作为 M7 gate 的前置。
