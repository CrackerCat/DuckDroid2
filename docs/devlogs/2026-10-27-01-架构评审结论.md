## 0. 总判断

骨架成立，可以冻结；但还不能直接开工。

**缺三块硬设计**（详见 `2026-10-27-02-调用桥与线程模型决策.md`）：

1. Guest ↔ Host 调用桥：guest 代码怎么调用到 host 的 C++ 实现
2. 阻塞 syscall 的完成语义（不重入）：futex_wait 睡下之后怎么恢复
3. 执行引擎的线程所有权模型：几个 engine、几个宿主线程、谁持有栈

**三处明显超前，v1 删除或降级**：TLS 三版本矩阵、HostThreadPool/跨实例 RunnableQueue、MemoryPool/Primordial/fork/warm pool/Web。

---

## 1. 冻结项（后续实现不得违背）

- `RuntimeInstance` 是唯一门面，禁止 `getMemory()/getThreads()`
- 每份状态有且只有一个所有者
- **CodeWriteNotifier 是 SMC 的正确性来源**，`tlb_epoch` 只是优化提示
- 语义事件同步可靠 / 诊断事件异步可丢，两条通道物理分离
- `目录说明.md` 的禁用目录清单
- 用 integration 测试当里程碑（顺序需按 §2.4 修正）

## 2. 降级与删除清单

| 项目 | 原位置 | v1 决定 | 理由 |
|---|---|---|---|
| TLS 布局 12/13/14 三份 | 设计 §6.5、目录 `threads/tls/` | **只做一份，API 33** | 三份是纯维护税；按实际被读到的字段实现（slot0 self、slot1 pthread_internal_t*、slot2 errno、slot4 stack_guard、key_data、clear_child_tid），等真实目标踩到再扩 |
| HostThreadPool | 设计 §4.3、目录 `worker/host_thread_pool/` | **删除** | 每个 RuntimeThread 自带一个宿主线程，不需要池 |
| 跨 RuntimeInstance 的 RunnableQueue | 设计 §4.3、目录 `worker/runnable_queue/` | **删除** | 调度单位就是宿主线程自己，不存在"取一个 RuntimeThread 来跑" |
| 宿主线程亲和性优化 | 设计 §4.3 | **删除** | 前置问题消失 |
| MemoryPool（64GB 预留 + 分区） | 设计 §4.4、目录 `worker/memory_pool/` | 推迟到 v3 | v1 先按 region 直接 mmap；但"Memory 持有宿主后备"这个方向保留（见决策 02） |
| SharedReadOnlyPool | 设计 §4.5 | 推迟到 v3 | 单实例阶段没有收益 |
| PrimordialProcess / fork 隔离 | 设计 §3.3 | 推迟到 v3 | 服务化才需要 |
| warm pool / reset 复用 | 设计 §5.3 | 推迟到 M6 之后 | 先能签，再谈复用 |
| Web / UDS / HTTP | 目录 `src/protocol/http`、`src/web` | 推迟到 v4 | C++ 侧只保留 `protocol/messages/` 和 `protocol/routing/`；HTTP 解析放 Python 端 |
| Dynarmic 空目录 | 目录 `runtime/backend/dynarmic/` | **v1 不建** | 空壳会诱导占位代码；M7 再接 |
| 全量指令级 trace | 设计 §6.7 | 只在分析模式开 | Unicorn 的 `count` 预算本身就是每指令一个 `UC_HOOK_CODE`（`uc.c:1043`、安装于 `uc.c:1192`），生产模式等于每指令一次回调 |

## 3. 文档修正清单（源码依据）

| 位置 | 原文 | 实际 / 修正 | 依据 |
|---|---|---|---|
| 设计 §6.2 | "Unicorn：指令计数中断（uc_ctl）" | 不是 `uc_ctl`；是 `uc_emu_start` 的 `count` 参数，并且是**每指令 hook** | `uc.c:1192` 存 `emu_count`；`uc.c:1043-1051` `hook_count_cb` 每指令计数后 `uc_emu_stop` |
| 设计 §6.2（未写） | — | `timeout != 0` 时**每次 `uc_emu_start` 创建一个宿主线程**；`run_once` 不要每次带 timeout，watchdog 放实例层 | `uc.c:1036-1040` `enable_emu_timer` → `qemu_thread_create` |
| 设计 §6.3 | 只写了 host 写代码页的协议 | 还要覆盖 **guest 自己写代码页**（解壳/JIT）：W+X 区上加 `UC_HOOK_MEM_WRITE`，或永不映射可写代码页 | 设计缺口 |
| 设计 §4.4 | MemoryPool 宿主 VA 预留、`PROT_NONE` | 与 `uc_mem_map` 冲突（Unicorn 自己 mmap 后备）。改成 `uc_mem_map_ptr`（Memory 持有宿主后备）后成立 | `unicorn.h:1166`、`qemu/softmmu/memory.c:65` |
| 设计 §6.1 | Backend 归 RuntimeInstance | 仍成立，但内部要**每个 RuntimeThread 一个 `uc_engine*`** | 见决策 02 §4 |
| 设计 §6.8 | "RegisterNatives 拦截…不是 Linux SVC" | 采用 thunk 方案后，**它就是 SVC**，这句可删 | 见决策 02 §2 |
| 设计 §7 | 顺序：01–03 在 04 之前 | 01–03 必须用**裸机器码/平坦 blob**；`pthread_create` 是导入符号，真实 `.so` 要等 loader | 依赖关系 |
| 目录 §3 | `protocol/http/parser.cpp`（C++） | 与"HTTP 用 Python 写"矛盾；C++ 侧只保留 `messages/` + `routing/` | 待统一 |

补充：**必须明确"不加载真实 libc.so"**。`libc/liblog/libdl/libm` 是**虚拟模块**，只提供符号表 + host stub，不读文件。否则 loader 会卡在 bionic 的 `DT_NEEDED` 递归上。

## 4. 里程碑

> 本节是 2026-10-27 的评审快照。**执行期的唯一权威是 `docs/里程碑.md`**（含当前状态、九条探针清单、每阶段"明确不做"）。两者冲突时以 `docs/里程碑.md` 为准。

每个里程碑 = 一个可 review 的 PR + 一个必须通过的 gate。gate 不过，不写下一条。

| 里程碑 | 内容 | gate |
|---|---|---|
| **M0 探针** | 构建骨架 + 不抽象、直接调 Unicorn API 的 spike | `docs/devlogs/2026-10-27-03-M0探针结果.md` 九条结论全部有数据（清单见决策 02 §5） |
| **M1 最小闭环** | common(id/error/log) + memory(region 表、mmap/munmap/mprotect/MAP_FIXED、CodeWriteNotifier) + backend/unicorn + threads/tls(单线程、API33 TCB) + svc(dispatcher + memory/fs/misc) + thunk 页 | `01_tls_read`、`02_pure_native`（裸 blob） |
| **M2 可观测性** | EventBus 语义通道 + 诊断环形缓冲 + SVC 日志 + guest LR 回溯 + 未实现符号报告 | `02` 的完整 svc trace；未实现调用能 dump 调用栈 |
| **M3 线程** | clone(SETTLS/CLEARTID)、futex WAIT/WAKE、阻塞完成式（PendingSyscall）、每线程 engine、实例大锁、clear_child_tid → join | `03_pthread_join`（裸 blob），N 线程压测 |
| **M4 loader + 虚拟 bionic** | ELF、PT_TLS → TLS manager、DT_NEEDED 递归、RELATIVE/GLOB_DAT/JUMP_SLOT/TLS_*、符号作用域、.init_array、JNI_OnLoad、导入符号 → thunk、虚拟模块表 | `04_so_load`：加载带 `DT_NEEDED` 的真实 `.so` 并调用函数 |
| **M5 JNI** | JNIEnv/JavaVM 表、ABI adapter、RegisterNatives、局部/全局引用、String/Object/Class/System stub、Call*Method 回调 guest | `05_jni_stub` |
| **M6 真实目标** | 选定北极星 so，跑到签出一致结果；之后再做 reset/warm pool | 真实签名输出一致；`06_warm_pool_reset` |
| **M7 服务化** | fork 隔离、WorkerPool、UDS、warm pool、隔离策略 | `07_end_to_end` |

### 测试产物策略（不需要 NDK）

已验证：`clang --target=aarch64-linux-android31 -fPIC -shared -nostdlib` 可以直接产出 ARM64 `.so`，导入符号保持 `UND`，正好喂给虚拟 bionic。

- 01–03：裸 blob（汇编/C，`-nostdlib`，不经过 ELF loader）
- 04+：两个自建 `.so` 互链产生 `DT_NEEDED`，测试递归加载
- 真机/真实 APK 才需要 NDK
