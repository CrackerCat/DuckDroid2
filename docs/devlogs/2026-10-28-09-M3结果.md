## 3. 关键实现决定与设计的差异

1. **专用主线程已落地。** 实例创建时 spawn 一条宿主线程持有主 engine；`callFunction`
   投递 `(entry,args)` 并等 `call_done`。公开的 `RuntimeInstance::CallResult` 形状不变，
   01/02 行为不变。
2. **每线程 engine。** `UnicornBackend` 只持有非拥有指针；`createEngine` 在注册前重放全部
   region，之后所有 map/unmap/protect/TB 失效广播到全部 engine。
3. **clone 用 `uc_context_save/restore`。** 父线程在 hook 里保存（PC 已是 `svc+4`），
   子 engine 恢复后覆盖 SP/TPIDR/X0；`CLONE_SETTLS` 只写 TP，不碰 guest 的 TCB。
   `PARENT_SETTID`/`CHILD_SETTID`/`CLEARTID` 按 arm64 参数序（x2/x3）处理。
4. **阻塞 syscall 的完成点在被唤醒线程。** waker 只调 `complete()` 算出 x0 并存进
   `pending_result`，被唤醒线程恢复时写 x0、清 pending、发布 SvcEvent（`id` 在此时分配）。
   这样 trace 顺序等于 guest 的串行恢复顺序。
5. **线程退出顺序是“先记账，后唤醒”。** `Exited` 事件在 CLEARTID 写 0/futex_wake 之前发布；
   否则 joiner 可能先于事件观察到线程退出，压测里 created/exited 计数会抖。
6. **引擎销毁延后到 reaper。** 让退出线程自己 `uc_close` 会与父线程在 clone hook 里
   `uc_open`/映射新 engine 竞争。现在退出线程只发布事件与 CLEARTID；engine 由
   `reapExited()`（父线程、持执行锁）或 `stop()` 统一关闭。
7. **宿主 API 加执行锁。** `mapMemory/writeMemory/readMemory/registerHostFunction` 先拿
   `execution_mutex`（递归），避免在某个 engine 正在跑时从别的宿主线程改地址空间；
   hook 内同线程重入安全。
8. **测试流程改为 ctest 超时兜底。** guest 线程没有 Unicorn 超时（见 §4），
   `duckemu_add_integration_test` 统一 `TIMEOUT 60`。

## 4. 踩到的坑

### 4.1 Unicorn 的超时线程会误停下一轮运行（重要）

现象：03 压测约 8% 概率失败，报 `guest stopped outside the return trap`，
PC 恒为 `svc + 4`（clone 的 trap 之后一条）。

定位（临时给 `uc.c` 加日志后）：

```text
[UC] timer saw done uc=... elapsed=648518 timeout=5000000000
[UC] timeout      uc=... timeout=5000000000 elapsed=285321 emu=0
```

`uc.c` 的 `_timeout_fn` 轮询**非原子**的 `uc->emulation_done`：

```c
do { usleep(2); if (uc->emulation_done) break; }
while (elapsed < uc->timeout);
if (!uc->emulation_done) { uc->timed_out = true; uc_emu_stop(uc); }
```

一次运行结束时 `emulation_done` 置 true，超时线程跳出循环，但在执行
`if (!uc->emulation_done)` 之前被抢占；此时下一轮 `uc_emu_start` 已把
`emulation_done` 置回 false，超时线程便把**新一轮**在 `svc+4` 处停掉。
日志里 elapsed 只有 0.2–0.6 ms，而 timeout 是 5 s，与“超时”无关。

**对策**：M3 所有 `uc_emu_start` 一律 `timeout = 0`。线程只能通过 SVC stop 或 fault
离开；guest 死循环会挂住调用方，由 ctest 超时兜底。生产 watchdog 后续自建
（实例线程 + 跨线程 `uc_emu_stop`），不再用 Unicorn 的超时参数。

### 4.2 `callFunction` 等待条件包含 `stopping_`

`exit_group` 会 `cv.notify_all()` 所有线程；`callFunction` 若把 `stopping_` 也当完成条件，
会在 `handleRunOutcome` 写入 `exit_code` 之前返回，`exit_code` 为空。改成只等 `call_done`
（`finalizeThread` 保证 stop 时也会补上 `call_done`）。

### 4.3 `stop()` 持实例锁 join

`stop()` 在 `instance_mutex_` 内 join 宿主线程；退出线程的 `finalizeThread` 要拿
`instance_mutex_` 清理等待队列 → 死锁。改为锁外 join。

### 4.4 GCC 16 误报

`vector<pair<uint32_t, std::function<...>>>` 的拷贝赋值触发
`-Werror=null-dereference`（`stl_pair.h:618`）。三个 publish 都改成锁内**拷贝构造**。

## 5. 已知限制

- **饿死**：单核串行，父线程在 guest 里死循环会饿死子线程（设计 §12）。
- **无 watchdog**：guest 死循环挂住 `callFunction`；ctest `TIMEOUT 60` 是唯一兜底。
- **futex 面很窄**：只有 WAIT/WAKE；timeout 指针非 0、WAIT_BITSET、PI、requeue 都走 ENOSYS。
- **clone 只支持同进程线程**：无 `CLONE_VM|CLONE_THREAD` 一律 `-EINVAL`。
- **engine 生命周期仍与 guest 运行交错**：reaper 在 clone hook 里关旧 engine、开新 engine；
  目前压测稳定，若后续出现 Unicorn 内部竞争，再引入 engine 池/延迟回收。
- **真实 bionic `pthread_*` 未跑**：M3 按拍板先用裸 blob；等最小 bionic（静态程序 +
  最小 loader）跑起来后作为后续 gate。
