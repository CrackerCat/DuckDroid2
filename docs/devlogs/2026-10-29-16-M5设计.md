## 1. 目标

让 guest `.so` 看到真实 Android 的 JNI 契约：

- `JNIEnv*` / `JavaVM*` 可用，表项落到 thunk；
- `FindClass` / `GetMethodID` / `RegisterNatives` 语义成立；
- 动态注册的 native 能被 host 调起，native 也能经 `Call*Method` 调回；
- `libeleven` 的 `JNI_OnLoad` 真正执行，`data(I)Ljava/lang/String;` 进入注册表。

**不是**目标：模拟 ART、执行 Java 字节码、完整 Android 框架。

## 2. 关键决策

### 2.1 严格解析，没有隐含默认值

DuckDroid 的 JavaWorld 是「未知即造」：`ResolveMethodObject` 找不到就自动创建、
返回默认值，`last_missing_shim()` 事后告知；类/字段同理。分析时「环境没写」和
「环境写对了」跑出同样结果，这是误导源。M5 明确反过来：

| 操作 | 未声明时 |
|---|---|
| `FindClass` | 返回 `nullptr`，发布 `JniEvent(MissingClass)` + `DUCKEMU_WARN` |
| `GetMethodID` / `GetStaticMethodID` | 返回 `nullptr`，发布 `MissingMethod` |
| `GetFieldID` / `GetStaticFieldID` | 返回 `nullptr`，发布 `MissingField` |
| `RegisterNatives` | 返回 `JNI_ERR`：类或方法未由环境声明（静态性来自声明，JNI 不携带） |
| 未实现的 JNI 表项 | 专用 `jni:unsupported` 入口，发布 `UnsupportedFunction`，返回 0 |

JNI 的 `nullptr` 本身是真实语义（native 代码必须检查），不是「默认值」。
环境里的值（包名、设备型号、证书、时间）一个都不内置；`envs/` 里写了什么就有什么。

### 2.2 Java 环境补充 = C++ 代码

环境补充按**归属**分两级（2026-10-29 用户修正）：

| 位置 | 内容 | 谁维护 |
|---|---|---|
| `src/runtime/jni/envs/` | **平台级**补充：`java.lang`，以后 `android.os.Build`、`android.content.Context` 等 | runtime，跨目标复用 |
| `code/user_code/<case>/` | **目标项目**：目标类声明、目标专属的 Java 方法/常量 | 每个 so/app 一个项目 |

runtime 不出现任何具体目标的名字。目标项目暴露一个安装函数，由自己的
`main.cpp` **显式调用**，不依赖静态注册：

```cpp
// code/user_code/libeleven_case/libeleven_env.hpp
namespace duckemu::user::libeleven
{
Result<void> installEnvironment(runtime::jni::JavaWorld &world);
}

// main.cpp：create 之后、任何 loadLibrary 之前
auto installed = instance.installJavaEnvironment(&user::libeleven::installEnvironment);
```

- 这是唯一的接线点：看得见、顺序可控、没有静态初始化 / 链接裁剪的坑。
- `RuntimeInstance::installJavaEnvironment` 只允许在第一个模块加载前调用
  （`JNI_OnLoad` 在 `loadLibrary` 里跑，晚装等于没装，直接拒绝而不是假装成功）。
- 类声明、父类、方法/字段、shim 实现全部是代码；常量就是 `return "Pixel 6"`。
- `envs/all.cpp` 只安装平台级内置模块；目标包和测试包都由各自的 runner 显式安装。
- 不引入 JSON/YAML/DSL，不新增第三方依赖；也不需要改 `RuntimeConfig`。

一个目标项目里的一条声明长这样（`code/user_code/libeleven_case/`）：

```cpp
const uint64_t klass = world.declareClass(
	"com/yuanrenxue/.../ChallengeElevenFragment", /*super=*/"");
world.declareMethod(klass, "data", "(I)Ljava/lang/String;", /*is_static=*/true, {});
// native 方法的方法体不在这里：JNI_OnLoad 的 RegisterNatives 会把地址填进来。
```

### 2.3 每线程 JNIEnv

- 函数表只有一份，只读，guest 内存里一页（233 项）。
- `JNIEnv*` 是每线程的 8 字节槽，内容是函数表地址；按 `TPIDR_EL0` 延迟分配。
- `JavaVM*` 每实例一个。
- `GetEnv` / `AttachCurrentThread` 返回调用线程的 env；版本不合法返回
  `JNI_EVERSION`，不装作成功。
- 本地引用按线程分表；全局引用实例级，槽位可复用。

### 2.4 句柄模型

所有 guest 可见的 JNI 值都是 guest 地址，host 指针不进 guest 内存：

| 值 | guest 侧 | host 侧 |
|---|---|---|
| `jobject` / `jclass` / `jstring` | 8 字节 `GuestRef { uint64_t object; }` | `handle → ObjectRecord` |
| `jmethodID` / `jfieldID` | 16 字节占位记录 | `id → MethodRecord/FieldRecord` |
| `JNIEnv*` | 8 字节槽 → 函数表 | `tp → 槽地址` |
| `JavaVM*` | 8 字节槽 → invoke 表 | 单例 |

句柄槽从 JNI arena（`RuntimeMemory` 自管的一小块可增长区域）里 bump 分配；
字符串、方法记录同理。这样 native 即使对句柄做普通 load/store 也不会踩到空地址。

### 2.5 调用路径

```text
guest: ldr x8,[env]; ldr x8,[x8,#off]; blr x8
  -> thunk: svc #(0x8000|idx)
  -> SvcDispatcher: x0..x7 (+sp) -> HostCallArgs
  -> JniState::invoke(slot, args)
  -> world / refs / registry / shim
```

反方向只有一条路：`HostCallArgs::call_guest`（M4 落地的同 engine 嵌套
`uc_emu_start` + context save/restore，32 层上限）。`Call*Method` 指向的是一个
**已注册 native** 时才走它；指向 host shim 时直接在本线程执行。

M5 限定：整数/对象/void 返回值；浮点返回值与
`Call<Type>MethodV`（va_list）明确不支持并报 `UnsupportedFunction`；
变参 `Call<Type>Method` 只支持落在 x3..x7 的参数，超出（guest 栈参数）报不支持。
`HostCallArgs` 增加 `sp` 与 `tid`，为 M6 的栈参数留好位置，但 M5 不使用 `sp`。

### 2.6 JNI_OnLoad 时机

- `RuntimeInstance::loadLibrary` 在**本模块构造器全部跑完**之后、返回 handle 之前，
  查本模块的 `JNI_OnLoad` 并调用 `(vm, nullptr)`。
- 返回负数（`JNI_ERR`）→ `loadLibrary` 失败；M5 不校验版本号是否在支持区间
  （只要求非负），等真实目标踩到再收紧。
- 依赖模块不调用（与 `dlopen` 一致）。
- `run_module_initializers = false` 时不调用（M4.5 gate 行为不变）。

### 2.7 函数表布局

运行时自己定义 `jni_layout.hpp` 的槽序号，不 include Android 头。正确性由
单元测试 `jni_layout_test` 保证：该测试 include ROM 的
`libnativehelper/include_jni/jni.h`，逐项 `offsetof(JNINativeInterface_, X)` 与
我们的槽序号 × 8 比对。

libeleven 反汇编给出的实测锚点（`libeleven.so`，`JNI_OnLoad` @0x4139c）：

| 调用 | 偏移 | 槽 |
|---|---|---|
| `GetEnv(vm, &env, JNI_VERSION_1_6)` | JavaVM 表 +0x30 | 6 |
| `FindClass(env, ...)` | env 表 +0x30 | 6 |
| `RegisterNatives(env, cls, methods, 1)` | env 表 +0x6b8 | 215 |

`JNI_VERSION_1_6 = 0x00010006`；`JNI_OK = 0`、`JNI_ERR = -1`、`JNI_EVERSION = -3`。

### 2.8 观测

新增 `observer::JniEvent`（有生产者才建）：

```text
kind: MissingClass | MissingMethod | MissingField | UnsupportedFunction
class_descriptor / name / signature / slot / tid
```

`RuntimeInstance::addJniListener`。gate 断言「happy path 没有 missing 事件」，
严格模式的失败在 trace/日志里可见，而不是静默返回 0。

## 4. Guest 可见布局

```text
JNI 状态（每实例）
  jni.functions : 一页只读，233 × 8 字节，每项 = thunk 地址
  jni.vm        : 8 字节 -> JavaVM 表（一页只读，6 项）
  jni.arena     : 可增长，句柄/方法记录/字符串

每线程
  jni.env_slots[tp] : 8 字节 -> jni.functions

jobject 槽 (GuestRef)
  +0  u64  object   (对象记录地址；0 = null)

jmethodID / jfieldID 记录
  +0  u32  kind
  +4  u32  reserved
  +8  u64  ordinal     (宿主表的键)
```

## 7. 不做 / 已知限制

- 不嵌 JVM、不执行 Java 字节码；Java 方法全部是 host shim 或已注册 native。
- 233 项表只实现被真实消费者踩到的项；未实现项显式报错（不是静默 0）。
- 数组、`NewString`（UTF-16 输入）、浮点返回值/字段、`Call<Type>MethodV`、
  guest 栈上的变参参数：M6 再补。
- `GetStringUTFLength` / `GetStringUTFChars` 用标准 UTF-8，不是 modified UTF-8
  （NUL 与孤立代理项未特殊处理）；当前消费者全为 ASCII。
- `ReleaseStringUTFChars` 不回收 arena 内存；本地引用在线程退出时不回收。
- `System.currentTimeMillis` / `nanoTime` 直接读宿主时钟；M6 的确定性对拍需要
  可注入的时钟（与 DuckDroid 的 `SetWallTimeNs` 对齐）。
- 异常只保留 pending 标志（`Throw`/`ExceptionCheck`）；`ThrowNew` 丢消息。
- `MonitorEnter/Exit`、`DetachCurrentThread` 类 no-op 是因为 guest 执行已被
  实例级执行锁串行化；不是默认值。
- 不实现 `Java_*` 导出名到 native 的自动绑定；只做 `RegisterNatives`（M6 需要时再加）。
- `data(int)` 的算法与返回值不属 M5，M6 的验收线。

## 9. 实现进度（2026-10-29）

S1–S4 全部完成，S5 的文档与验证在本节收尾；`build` / `build-werror` /
`build-asan` 各 23 个测试全绿（M4.6 结束时 18 个）。

### 落地事实

- `JNIEnv` 表 233 项、`JavaVM` 表 8 项，全部由 `ThunkTable` 生成；表页只读。
  为了容纳 241 个新 thunk，`ThunkTable` 改为**按页连续增长**（每 512 项一页，
  地址仍是 `base + index * 8`），上限 0x7FFF。
- 每线程 `JNIEnv*` 是 8 字节槽，按 **live TPIDR_EL0** 延迟分配；dispatcher 现在
  在每次 trap 时读寄存器，而不是用 scheduler 缓存的 `tls_tp`。
- 严格性补强：所有 `jclass` 句柄都要求解析后是**类对象**，否则按缺失处理；
  `RegisterNatives` 只绑定环境已声明的方法（静态性来自声明）。
- `HostCallArgs` 增加 `sp` 与 `tid`；`sp` 为 M6 的栈参数预留，M5 不读取。
- 归属修正（2026-10-29 用户指出）：目标专属声明从 `runtime/jni/envs/` 挪到
  `code/user_code/libeleven_case/libeleven_env.cpp`；随后再把隐式静态注册改成
  **显式 `RuntimeInstance::installJavaEnvironment()`**（用户质疑 main.cpp 里看不到
  调用），接线点只剩 main.cpp 一行。runtime 的 `envs/` 只剩平台级 `java.lang`，
  且不再出现 `libeleven` 字样。

### 实测结果

- `05_jni_real`：libeleven 的 `JNI_OnLoad` 执行成功（返回非负版本号才允许
  `loadLibrary` 返回；实测返回 `0x10006`），`RegisterNatives` 把
  `data(I)Ljava/lang/String;` 绑定到 `JNI_OnLoad - 0x4139c + 0x40cb4`，
  测试逐字节地址比对通过。
- `05_jni_env` / `05_jni_stub`：fixture 走通 FindClass / GetStaticMethodID /
  CallStaticIntMethod / NewStringUTF / GetStringLength；host→guest、guest→host、
  guest→guest（嵌套）三个方向均返回 42；严格缺失事件按预期出现。
- `jni_layout_test` 把 30 个槽位与 ROM `jni.h` 的 `offsetof` 逐项比对，含
  `FindClass=0x30`、`RegisterNatives=0x6b8`、`JavaVM::GetEnv=0x30`。

### 发现并修复的旧 bug

`callGuestNested`（M4 落的 host→guest 嵌套桥）在 `uc_context_restore` **之后**
读 x0，拿到的是外层 guest 的 x0（通常是 `JNIEnv*`），不是嵌套调用的返回值。
`pthread_once` 不关心返回值，所以 M4/M4.6 一直没暴露；M5 的 `Call*Method`
第一次需要嵌套返回值时立刻失败（返回了 env 指针）。修复为**先读 x0 再恢复上下文**。
