## 0. 结论摘要

| # | 设计假设 | 实测 | 判定 |
|---|---|---|---|
| 1 | `svc #0` → `UC_HOOK_INTR`，`intno == 2` | `intno = 2`，hook 恰好一次 | ✅ |
| 2 | hook 里 PC == `svc + 4` | `0x10008 == 0x10004 + 4` | ✅ |
| 3 | 不碰 PC、写 x0，guest 从下一条继续 | x0 被改写为 `0xCAFE`，随后 `add #1` 得 `0xCAFF` | ✅ |
| 4 | hook 内 `uc_emu_stop()`，PC 停在 `svc+4`；宿主写 x0 后能续跑 | PC=`0x10018`=`svc+4`；x5/SP/内存全部保留；续跑 x1=`0x43`；hook 未重入 | ✅ |
| 5 | `mrs x0, tpidr_el0` 读到宿主写入的 `UC_ARM64_REG_TPIDR_EL0` | 两次改 TLS 基址（`0x40000`/`0x41000`）均正确 | ✅ |
| 6 | 同 engine 嵌套 `uc_emu_start`，记下可用层数 | 可用；但**嵌套调用会覆盖外层寄存器/PC**，必须 `uc_context_save/restore`。总层数 64 时 Unicorn 内部损坏并段错误 | ⚠️ 有修正 |
| 7 | 两个 engine 两条宿主线程，`uc_mem_map_ptr` 共享内存 | 双引擎真并发跑完，互相可见写，宿主也看到 | ✅ |
| 8 | `uc_mem_map_ptr` + `uc_mem_protect`：engine 权限独立，宿主映射不受影响 | 同一宿主页：A RW 可写，B RX 写失败、可执行；A 自己 protect 后只读，B 不受影响；`/proc/self/maps` 始终 `rw-p` | ✅ |
| 9 | 跨线程 `uc_emu_stop`；暂停中 map/protect/`uc_ctl` 安全 | stop 延迟 7µs，`UC_ERR_OK`；暂停中 map/protect/TB cache 操作全 OK；可续跑 | ✅ |

**必须写回设计的两条修正**

1. **嵌套 `uc_emu_start` 不是透明的。** 同一 engine 只有一个寄存器组：嵌套 run 结束
   后，外层的 PC 和通用寄存器就是嵌套 run 最后的状态。实测不保存上下文时，32 层
   嵌套里只有最内层执行了 `svc` 之后的代码（内存计数器 = 1）；用
   `uc_context_save/restore` 包住每次嵌套调用后，33 层全部正确续跑（计数器 = 33）。
   这直接否定决策 02 §4.5 的“`uc_context_save/restore` 不再需要”——该结论只在
   **跨线程**成立，同 engine 的 host→guest 回调必须自己保存/恢复。
2. **`UC_MAX_NESTED_LEVEL = 64` 是纸面值，64 层的边界不可用。**
   总嵌套 63 层（= 62 次嵌套重入）正常；总嵌套 64 层（= 63 次重入）时
   `uc->nested_level` 被写坏（gdb 读到 `0x557c913e`），随后在
   `include/uc_priv.h:464` 的 `uc->exits[uc->nested_level - 1]` 段错误。
   64MB 宿主栈同样复现，不是栈溢出。实现里应硬性限制在 32 层以内。

## 1. Probe 1：`svc #0` → `UC_HOOK_INTR`，`intno == 2`

代码：`mov x8, #98; svc #0; mov x0, #0x1234; b done`。

```
svc address                                    0x0000000000010004
intr hits                                      1
intno passed to hook                           2
x8 seen in hook                                0x62
uc_emu_start                                   UC_ERR_OK
```

- `intno` 就是 `cpu->exception_index`，即 `EXCP_SWI = 2`，与
  `qemu/target/arm/cpu.h:33` 一致。可以用它区分 SVC 和其他异常。
- 寄存器在 hook 里可读；非阻塞 syscall 的返回值直接写 x0 即可。

## 2. Probe 2：hook 里 PC == `svc + 4`

```
svc address                                    0x0000000000010004
PC in hook                                     0x0000000000010008
svc + 4                                        0x0000000000010008
```

与决策 02 §3.2 的源码结论一致（`translate-a64.c:14514` 先 `pc_next += 4`）。
**SVC 分发器不需要做任何 PC 补偿**。

## 3. Probe 3：不碰 PC + 写 x0，继续执行

Guest：`mov x0, #0xDEAD; svc #0; add x0, x0, #1; b done`，hook 里把 x0 改成
`0xCAFE`。

```
x0 written by hook                             0xCAFE
x0 after add #1                                0xCAFF
PC after run                                   0x0000000000010010 (= until)
hook ran                                       1 次
```

非阻塞路径的结论成立：hook 返回后 guest 从 `svc+4` 继续，寄存器写入生效。

## 4. Probe 4：hook 内 stop，宿主写 x0，再从 `svc+4` 续跑

Guest：`mov x5,#0x7777; str x5,[data+8]; mov x0,#0xDEAD; svc #0; add x1,x0,#1;
str x1,[data+16]; b done`。hook 里记录现场、写 x0=`0x1111`、`uc_emu_stop()`。

```
first uc_emu_start                             UC_ERR_OK
PC after stop                                  0x0000000000010018
svc + 4                                        0x0000000000010018
x0 after stop                                  0x1111
x5 before/after stop                           0x7777 / 0x7777
SP before/after stop                           0x30ff0 / 0x30ff0
mem[data+8] before stop                        0x7777
hook hits after first run                      1
--- 宿主写 x0=0x42，从 0x10018 再次 uc_emu_start ---
second uc_emu_start                            UC_ERR_OK
x1 after resume                                0x43
mem[data+16] after resume                      0x43
hook hits after resume                         1   (没有重放)
```

这正是决策 02 §3 的“完成式”模型：停住 → 宿主补返回值 → 从 `svc+4` 续跑，
同一个 svc 只进 handler 一次。PC、通用寄存器、SP、guest 内存全部跨 stop/start 保留。
（恢复时 `uc_emu_start` 的 `begin` 显式传当前 PC。）

## 5. Probe 5：`mrs x0, tpidr_el0`

Guest：`mrs x0, tpidr_el0; ldr x1, [x0]; b done`。宿主映射 TLS 页并写入
“slot 0 = 自身地址”。

```
tls = 0x40000: x0 = 0x40000, x1 = 0x40000
tls = 0x41000: x0 = 0x41000, x1 = 0x41000
TPIDR_EL0 readback = 0x41000
```

- `UC_ARM64_REG_TPIDR_EL0` 可写、可读回，`mrs` 立即生效。
- 两次 run 之间切换 TLS 基址没有残留。M1 的 TLS 实例分配可以按“每次进入
  RuntimeThread 前写 TPIDR_EL0”实现。
- 注意：本探针只验证了地址寄存器和 slot 0 读取，真实 bionic TCB 布局留给 M1。

## 6. Probe 6：同 engine 嵌套 `uc_emu_start`

Guest 每层执行 `svc #1`，hook 里再嵌套一次同一个 run；每层在 `svc` 之后对
**guest 内存**计数器 +1（内存不属于 CPU context，能区分“这一层真的续跑了”）。

默认 `limit = 32`（`DUCKEMU_NEST_LIMIT` 可覆盖）：

```
-- 不保存 context --
max hook depth (= total emu_start levels)      33
successful nested uc_emu_start calls           32
guest-memory counter after unwind              1     <-- 只有最内层续跑了
PC after outer run                             0x10014
elapsed / nested total                         158us / 1555us

-- 每次嵌套用 uc_context_save/restore --
max hook depth                                 33
successful nested calls                        32
guest-memory counter after unwind              33    <-- 每层都续跑了
elapsed / nested total                         345us / 4550us
```

结论：

- **嵌套本身可用**，不需要为每层新建 engine（决策 02 §4.2 方向正确）。
- **同一 engine 是一个寄存器组**。嵌套 run 结束时 PC/寄存器是它最后的状态；
  外层 hook 返回后不会再回到自己的 `svc+4`。需要外层继续执行时，必须：
  ```cpp
  uc_context_save(uc, ctx);
  uc_emu_start(uc, begin, until, 0, 0);
  uc_context_restore(uc, ctx);
  ```
- 代价：本例 32 次嵌套，save/restore 增量约 `(4550-1555)/32 ≈ 94µs`/次
  （Release，包含探针自身的计时开销；M5 的 `Call*Method` 是低频路径，可接受，
  但不要把它放进热循环）。
- **层数上限（实测）**：
  - 总嵌套 63 层（`DUCKEMU_NEST_LIMIT=62`，62 次重入）：正常。
  - 总嵌套 64 层（`DUCKEMU_NEST_LIMIT=63`）：SIGSEGV。
  - 把宿主栈提到 64MB 仍复现，不是宿主栈溢出。
  - gdb：崩溃点 `include/uc_priv.h:464`，`uc->nested_level` 被写成
    `0x557c913e`（一个指针的低 32 位，`0x5555557c9140` 附近是 CPUState）。
    `UC_MAX_NESTED_LEVEL = 64` 的 `jmp_bufs[64]` 边界实际不可用。
  - 实现约束：`RuntimeInstance` 对 host→guest 回调做**硬深度上限 32**，
    超限直接报错，不依赖 Unicorn 的 64。

## 7. Probe 7：两个 engine、两条宿主线程、`uc_mem_map_ptr`

A/B 两个 engine 各自映射同一块宿主页到 guest `0x50000`。Guest 握手：

- A：`phase=1` → 自旋等 `phase==2` → 写 `ack=0xAAAA`、`phase=3`
- B：自旋等 `phase==1` → 写 `marker=0xBBBB`、`phase=2` → 自旋等 `phase==3`

```
A uc_emu_start / B uc_emu_start                 UC_ERR_OK / UC_ERR_OK
shared[0] phase                                3
shared[1] A ack                                0xAAAA
shared[2] B marker                             0xBBBB
elapsed                                        236us
sampled both-in-emu overlap                    1
```

- 两个 guest 都在等对方写，而 `uc_emu_start` 不会主动让出；能同时跑完就证明两条
  宿主线程上的两个 engine 是**真并发**执行的（串行模型会死锁到 5s 看门狗）。
- `uc_mem_map_ptr` 后，一个 engine 的写立刻对另一个 engine 和宿主可见；
  数据一致性不需要额外同步。
- 这个探针只覆盖“两个 engine 同时跑 + 共享内存”。futex 语义、N 线程压测留给 M3；
  原子指令（LDXR/STXR/LSE）在多 engine 并发下是否正确，仍按决策 02 §4.4 用实例级
  大锁规避。

## 8. Probe 8：`uc_mem_map_ptr` + 权限

同一宿主页（`/proc/self/maps` 为 `rw-p`），A 映射 RW，B 映射 RX；随后 A 单独
`uc_mem_protect(READ)`：

```
A guest 写 canary                              UC_ERR_OK；宿主字节 = 0x5A
B guest 写同一页                               UC_ERR_WRITE_PROT (12)，宿主字节仍 0x5A
A 从 RW(无EXEC) 映射取指                       UC_ERR_FETCH_PROT (14)
B 从 RX 映射取指（stub: ldrb）                UC_ERR_OK；读到 0x5A
A uc_mem_protect(READ)                         UC_ERR_OK
A guest 写                                     UC_ERR_WRITE_PROT
宿主直接写字节 0x77                           成功
A guest 读                                     0x77（READ 仍允许）
B 取指 / 读                                    仍成功，读到 0x77（A 的 protect 不影响 B）
/proc/self/maps before map_ptr / after protect rw-p / rw-p
```

结论：

- `uc_mem_map_ptr` 的权限是 **per-engine** 的；同一宿主后备可以“A 可写、B 只执行”。
- `uc_mem_protect` 只改模拟语义，**不 mprotect 宿主内存**（宿主始终可读写，
  `/proc/self/maps` 不变）。决策 02 §4.5 的结论成立。
- 写保护、取指保护的错误码分别是 `UC_ERR_WRITE_PROT`、`UC_ERR_FETCH_PROT`，
  M1 的 memory handler 可以直接映射到 `-EFAULT`/`-EPERM` 一类的 guest 语义。
- 说明：本探针在宿主侧直接调用 `uc_mem_protect` 来代表“guest 发起 mprotect 后
  backend 要做的动作”。真正的 guest `mprotect` syscall 分发在 M1 实现，不在 M0。

## 9. Probe 9：跨线程 stop + 暂停中操作

Guest：`loop: add x0,x0,#1; b loop`，主线程等 guest 真正开跑 50ms 后从另一条
线程调用 `uc_emu_stop`。

```
uc_emu_stop from another thread                UC_ERR_OK  (延迟 7us)
uc_emu_start return                            UC_ERR_OK
instructions executed before stop              0x4365ee（含 UC_HOOK_CODE 每指令回调）
PC after stop                                  0x10004
--- 引擎空闲（paused）时，从主线程操作 ---
uc_mem_map / uc_mem_protect                    UC_ERR_OK / UC_ERR_OK
uc_ctl_remove_cache / uc_ctl_flush_tb          UC_ERR_OK / UC_ERR_OK
uc_query(PAGE_SIZE/ARCH/MODE)                  OK；0x400 / 2(ARM64) / 0(ARM)
--- 从 stop 的 PC 续跑，timeout=100ms ---
uc_emu_start                                   UC_ERR_OK
uc_query(TIMEOUT)                              timed_out = 1
instructions after resume                      0xfe2b83（继续增长）
PC after resume                                0x10004
```

结论：

- **跨线程 `uc_emu_stop` 可用**：返回值、延迟、PC 都正常，`uc_emu_start` 以
  `UC_ERR_OK` 返回。实例级 watchdog 线程的方案成立。
- 暂停中的 engine 上做 map/protect/TB cache 操作是安全的，且之后能继续跑。
- 注意：`uc_emu_start` 带 `timeout` 时**不会**返回错误码，而是正常返回 +
  `uc_query(UC_QUERY_TIMEOUT)` 标志。M2/M3 的超时处理必须查这个标志，
  不能只看 `uc_err`。
- 附带发现：`UC_QUERY_PAGE_SIZE` 默认是 `0x400`（Unicorn ARM64 的
  `TARGET_PAGE_BITS_MIN = 10`）。**M1 必须在首次 `uc_emu_start` 前用
  `uc_ctl_set_page_size(uc, 0x1000)`**（或按目标 Android 的 16KB 页）把模拟页
  对齐到 Android 语义，否则 guest 的 mmap/mprotect 粒度会和真机不一致。
  （本探针所有映射都用 4KiB 对齐，不受影响。）

## 10. 对设计/里程碑的修正清单

| 位置 | 原文 | 修正 |
|---|---|---|
| 决策 02 §4.5 | “`uc_context_save/restore` 不再需要” | **只在跨线程成立**。同 engine 的 host→guest 嵌套回调必须在每次嵌套前后 save/restore，否则外层 PC/寄存器被嵌套 run 覆盖 |
| 决策 02 §4.2 | 嵌套 `uc_emu_start` 即可 | 方向成立，但需加上一条：嵌套调用不恢复外层寄存器组 |
| 决策 02 §4.2/证据索引 | `UC_MAX_NESTED_LEVEL = 64` | 纸面 64；实测总嵌套 64 层会破坏 `nested_level` 并段错误。**实现硬上限 32 层总嵌套**，超限报错 |
| M1 内存 | — | 首次 run 前设置 Unicorn 页大小（Android 4KB；16KB 页设备另算） |
| M2/M3 超时 | — | `uc_emu_start` 的 timeout 不靠返回码，必须查 `UC_QUERY_TIMEOUT` |
| M5 JNI | — | `Call*Method` 的嵌套返回依赖 context save/restore；深度上限 32 |

### 对后续里程碑的直接影响

- **M1**：SVC 分发按“PC 不动”实现；非阻塞写 x0/d0；阻塞用 `uc_emu_stop` 挂起；
  MemoryManager 的 map/protect 直接映射到 `uc_mem_map_ptr`/`uc_mem_protect`，
  权限按 engine 分别设置。
- **M2**：`UC_HOOK_INTR` 足够拿到 SVC 事件（intno=2 + x8 + 参数寄存器）；
  指令级 trace 仍只在分析模式开。
- **M3**：watchdog 用跨线程 `uc_emu_stop`；futex 阻塞后线程退出 `uc_emu_start`，
  大锁释放。两 engine 共享内存已实测可行。
- **M5**：每次 host→guest 回调包 save/restore，嵌套深度计数并限 32。

## 11. M0 未覆盖（明确留给后续）

- 真正的 guest `mprotect`/`mmap` syscall 分发（M1）。
- “engine 正在执行时”从另一线程做 map/protect（本探针只测了暂停中）。
- 多 engine 真并发下的原子指令/futex 正确性（M3，且按决策 02 用大锁规避）。
- `count` 预算与 `timeout` 的精确开销（M2 观测模式再测）。
- 16KB 页 Android 目标的页大小配置（北极星确定后）。
- 指令级 trace 的性能预算（M2）。

## 12. 复现与原始数据

- Spike：`code/tools/spike/unicorn_spike.cpp`（单文件，无 runtime 抽象）。
- 一次 `all` 的完整输出在本机为 189 行；本文引用了所有断言与关键数值。
- 层数边界实验：
  ```bash
  DUCKEMU_NEST_LIMIT=62 ./build/unicorn_spike 6   # 63 层总嵌套，通过
  DUCKEMU_NEST_LIMIT=63 ./build/unicorn_spike 6   # 64 层，SIGSEGV
  (ulimit -s 65536; DUCKEMU_NEST_LIMIT=63 ./build/unicorn_spike 6)  # 仍 SIGSEGV
  ```
- 崩溃现场（RelWithDebInfo + gdb）：
  ```
  #0 uc_addr_is_exit (uc=..., addr=65548) at include/uc_priv.h:464
  (gdb) p/x uc->nested_level
  $1 = 0x557c913e
  ```
