## 3. 关键实现决定

1. **一个 syscall 一条记录。** `seq` 在进入分发时分配（调用顺序），`id` 在发布前分配
   （发布顺序，`svc.log` 首列）。M2 两者同序；M3 的阻塞 syscall 晚完成后，`seq` 在文件里
   可能不再单调，但首列 `id` 始终单调连续，解析器不用改。一个 syscall 永远只有一条记录
   （决策 02 §3.1）。
2. **trace 每行 flush。** 文件必须在实例存活期间可读（测试就是这么读的），svc 频率低，
   `fflush` 每行无成本压力。
3. **`args` 是寄存器快照，不是按签名裁剪的参数。** 未使用的 x 寄存器带着 ABI 残留
   （例如 getpid 的 `0x40017000`），这是刻意的：不引入 syscall 参数表，也避免"猜"签名。
4. **帧 0 是 `svc` 指令地址**，其余帧是保存的 LR（调用点 + 4）；名字沿用 bl.log 的
   `模块!偏移` 降级约定，命中不了 region 时为裸地址。
5. **`callFunction` 先把 `X29` 清零**，给帧链一个终止符；否则首次运行会读到脏 x29。
6. **回溯每步都校验**：16 字节对齐、仍落在 `SP` 所属 region 内、16 字节可读、LR 非 0、
   帧数上限 32。任何一步失败都停止并把原因写进 `note.stop` —— 不猜帧。
7. **诊断通道**：生产者是 `UC_HOOK_MEM_READ|WRITE`（只收成功访问），SPSC 环满时**丢最新**
   并计数；M2 的消费者是宿主 `drainDiagnostics()`，不开后台线程。
8. **`MemoryEvent` 只在公开入口发一条**：`map/mapFixed/unmap/protect/brk`（成功的），
   `MAP_FIXED` 的内部拆分与隐式 unmap 不单独发。
9. **格式定义只有一份**：`svc_trace` 同时提供 `formatSvcTraceLine` / `parseSvcTraceLine`，
   gate 测试与 `trace_viewer` 共用。
10. **事件类型按生产者裁剪**：只建 `SvcEvent` / `MemoryEvent`；`ModuleEvent`（M4）、
    `ThreadEvent`（M3）等到有生产者再建。

### 与设计文档的差异

- `RingBuffer` 的并发单元测试用 `capacity > 总数` 来断言"无序丢失"，因为 `tryPush` 在满时
  按设计丢弃，无法在溢出场景下断言零丢失；溢出行为由单线程用例覆盖。
- `trace_viewer` 的 `ret` 同时打印有符号（`-38`）与十六进制，便于人读。
- `name` 列会把 `\t` / `\n` / `\r` 替换成 `_`：host stub 名是开发者提供的，一个制表符就会
  让后面所有列错位；这是防御性处理，不改变正常名字。

## 4. 已知限制（M2 明确没做）

- **帧链是 frame-pointer 回溯，不是 CFI/DWARF。** Android release 构建默认
  `-fomit-frame-pointer`，真实 .so 上链会很短；M4 真正加载 .so 后再决定要不要上 CFI。
- 指令级 trace（`count` 预算 + watchdog）未实现；诊断通道只有内存访问事件。
- 没有异步消费者线程、没有 trace 轮转/背压 —— M2 的 svc 频率用不上。
- `ModuleEvent` / `ThreadEvent` 未建；符号名解析要等 loader。
- 文件 mmap、阻塞 syscall 等语义仍旧是 M4 / M3 的事。

## 6. 评审后的修正（同日）

三处修正，原则都是**不靠约定、靠结构**。

### 6.1 trace 写入者改为共享所有权

原实现：`Impl::trace` 是 `unique_ptr`，listener 捕获裸指针，正确性依赖"`trace` 声明在最后
→ 最先析构"这条声明顺序契约（`runtime_instance.cpp` 里那条 `Declared last` 注释）。

现在：listener 捕获 `shared_ptr<SvcTraceFile>`，文件由 bus 与 listener 共同持有。任何析构
顺序都不会悬垂，也不再需要"哪个成员声明在最后"这种编译器不检查的知识。代价是文件晚一点
关闭——它本来也是最后一个需要关闭的东西。

### 6.2 listener 重入保护

`publishSvc` 在 Unicorn 的 hook 内同步执行。listener 若调用 `RuntimeInstance::callFunction`
（或任何再次 `uc_emu_start` 的路径），就是同一 engine 上的嵌套运行，嵌套结束会覆写外层的
PC/GPR —— M0 探针 6 实测：不保存上下文时 33 层嵌套里只有最内层继续正确。

现在：`EventBus` 在调用 listener 期间把 `deliver_depth_` 加一并暴露 `delivering()`；
`RuntimeInstance::callFunction` 发现它非零直接返回 `InvalidArgument`。保护点在**引擎入口**，
不在 bus（bus 里 publish 套 publish 只是递归调 listener，不碰引擎）。
`02_pure_native` 增加断言：listener 里调 `callFunction` 必须失败。

实现这道保护时发现一件事：**svc 路径本来就有第二道防线** —— `Impl::state` 在 `run()` 期间是
`Executing`，listener 里再调 `callFunction` 会先被 "not Ready" 拒绝。所以测试改用**内存事件
通道**（`mapMemory` 在引擎空闲时发布 `MemoryEvent`，实例仍是 Ready，只有 `delivering()` 拦
得住），否则拿掉新保护后测试照样通过。已用变异验证：注释掉 `delivering()` 判断，
`02_pure_native` 恰好 1 条断言失败；恢复后全绿。

### 6.3 svc.log 首列改为 `id`，`seq` 退到第二列

`seq` 是**调用顺序**（进入时分发）。M3 的阻塞 syscall 会在稍后完成：若拿它当首列，文件
行序会非单调，破坏"首列单调连续、可二分"的家族约定（`TraceFormat.md` 对 code.log 的
行号就是这么用的）。

新增首列 `id` = **发布顺序**（发布前分配），恒单调连续；`seq` 保留调用顺序。
M2 两者相同（同步完成），差别要到 M3 才出现，但格式现在定死，M3 不改解析器。

### 6.4 评审中确认不做/留到后续的两条

- **`MemoryEvent` 不是账本。** `MAP_FIXED` 的内部 unmap/split 与 `mprotect` 的 split 不发
  事件，所以事件流**重建不出 region 表**，只能回答"谁在哪一刻动了哪一段"。M2–M4 的问题是
  后者，故保持现状；真需要账本时（loader 排水重叠映射）再加 implicit unmap 事件或
  `dumpRegions()` 快照，不把事件流做成半吊子 journal。
- **诊断环是 SPSC，M3 必须改成每线程一个环，不能加锁。** 生产者是每条 guest 访存都会走的
  热路径，加锁等于让观测拖垮执行。`RuntimeThread` 各自持环、宿主 drain 时遍历，
  `drainDiagnostics` 的接口形状已经兼容这次拆分。
