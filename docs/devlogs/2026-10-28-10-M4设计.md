## 1. 范围与 gate

M4 让 guest 从"手搓裸 blob"变成"跑磁盘上的 `.so`"：解析 ELF、映射段、递归依赖、
重定位，把未定义符号接到 host thunk。

gate：

- `tests/integration/04_so_load.cpp`：加载带 `DT_NEEDED` 的真实 `.so` 并调用函数
- 虚拟模块解析：`write` / `malloc` / `pthread_once` 落到 host stub
- 未解析符号：错误信息带符号名 + 模块名，并复用 M2 的 guest 栈 dump
- 回归：`01`–`03` 全绿；Release / `-Werror` / ASan 三套

## 2. 模块模型

```cpp
struct Module {
    std::string path;          // 虚拟模块为空
    std::string soname;
    uint64_t base;             // load bias；模块内 VA = base + st_value
    bool is_virtual;
    std::vector<Segment> segments;   // 只留需要的元数据，不复制全部 phdr
    SymbolTable symbols;       // dynsym + strtab + hash
    TlsTemplate tls;           // PT_TLS 原样
    std::vector<std::string> needed;
    GuestVA init_function;     // DT_INIT
    GuestVA init_array;        // DT_INIT_ARRAY + size
    State state;               // Loading → Loaded
};
```

`ModuleRegistry`：`soname → Module`，外加 handle（`uint64_t`，单调递增）给宿主 API。
已加载模块按 soname 去重；同一个路径再次 `loadLibrary` 返回同一 handle。

## 3. 地址空间与布局

现有约束：

- `next_free_` 从 `0x40000000` 向上（stack/TLS/mmap 都在这片）
- thunk 页固定 `0x70000000`，堆固定 `0x30000000`
- `map()` 会跳过已占用区间，不会覆盖

模块槽取 **`0x60000000` 起，每模块 16 MiB 步进，`base` 按 `p_align` 向上对齐**。
选择理由：落在 `next_free_` 与 thunk 页之间，且 `map()` 的跳过逻辑能避开它。

映射规则：

- 每个 `PT_LOAD` 用 `mapFixed(base + pageDown(p_vaddr), pageUp(p_memsz), perms, "module:<soname>")`
- `p_filesz` 部分写文件内容；`p_memsz - p_filesz` 保持零（`mapFixed` 的宿主 `mmap` 本来就是零页）
- 若两个 `PT_LOAD` 映射后重叠（畸形文件或对齐不足）→ `InvalidArgument`，不静默合并
- 全部走 `RuntimeMemory::mapFixed`，因此 MemoryEvent / engine 广播 / 执行锁自动生效；
  loader 自己**不碰** `uc_engine`

`.bss`、`.data.rel.ro` 的重定位写入都走 `RuntimeMemory::write`。

## 4. ELF 解析

自己写（third_party 要报批），只支持 `ELFCLASS64` / `EM_AARCH64` / `ET_DYN`。

读的字段：

| 来源 | 用途 |
|---|---|
| `e_phoff/e_phnum` | `PT_LOAD`、`PT_TLS`、`PT_DYNAMIC` |
| `PT_LOAD` | vaddr/filesz/memsz/flags/align |
| `PT_TLS` | filesz/memsz/align + 初始化镜像（在文件里的偏移） |
| `DT_NEEDED` | 依赖 |
| `DT_SONAME` | 注册键；缺失时用文件名 |
| `DT_SYMTAB` / `DT_STRTAB` / `DT_STRSZ` | 动态符号表 |
| `DT_GNU_HASH` / `DT_HASH` | 查表；两者都没有时线性扫描 dynsym |
| `DT_RELA/RELASZ`、`DT_JMPREL/PLTRELSZ/PLTREL` | 重定位 |
| `DT_INIT`、`DT_INIT_ARRAY/ARRAYSZ` | 构造 |
| `DT_RELR`、`DT_ANDROID_REL(A)` | **检测到即报错**，见 §12 |

地址换算一律 `base + st_value`；`st_value == 0` 且 `st_shndx == SHN_UNDEF` 表示未定义。

## 5. 符号与作用域

查表顺序（贴合 bionic 的全局组语义，但按 M4 需要简化）：

```text
for module in [请求方, 请求方的 NEEDED 闭包（BFS 顺序）, 全局已加载（RTLD_GLOBAL）]:
    if 命中: return base + st_value
virtual module 表（libc/liblog/libdl/libm）:
    if 命中: return thunk VA（按需创建）
未命中: 未定义
```

- **弱未定义符号**（`STB_WEAK` + `SHN_UNDEF`）解析失败时写 0，不报错
- **符号版本**（`DT_VERSYM`/`DT_VERNEED`）**不实现**：按名字匹配，忽略版本。真实 Android
  `.so` 的 `LIBC` 版本要求因此被跳过；M6 若踩到再补
- **IFUNC**（`STT_GNU_IFUNC`）不实现；解析到即报错并打印符号名
- 未定义的**函数**符号 → thunk；未定义的**数据**符号（`STT_OBJECT`，如 `environ`）→
  报错。thunk 只能当函数指针用，这是 M4 的硬边界

## 6. 重定位

| 类型 | 处理 |
|---|---|
| `R_AARCH64_NONE` | 跳过 |
| `R_AARCH64_RELATIVE` (1027) | `base + addend` |
| `R_AARCH64_ABS64` (257) | `S + A` |
| `R_AARCH64_GLOB_DAT` (1025) | `S`（写 GOT） |
| `R_AARCH64_JUMP_SLOT` (1026) | `S`（写 PLT GOT） |
| `R_AARCH64_TLS_TPREL64` (1031) | `offset_from_tp + A`，见 §8 |
| `R_AARCH64_TLS_DTPMOD64` / `TLS_DTPOFF64` (1028/1029) | 报错（需要 DTV） |
| `R_AARCH64_TLSDESC` (1032/1033) | 报错，错误信息提示"Android 默认 TLS 模型未支持" |
| 其他 | 报错，带类型号、符号名、模块名 |

- **只做立即绑定**，不实现惰性 PLT（`DT_PLTGOT` 不参与）
- 重定位写入一律 `RuntimeMemory::write`
- 应用顺序：依赖先于依赖方（后序）；`DT_RELA` 先于 `DT_JMPREL`

## 7. DT_NEEDED 与虚拟模块

依赖解析顺序：

1. **虚拟模块表**：`libc.so`、`liblog.so`、`libdl.so`、`libm.so`（按 soname 精确匹配）
2. **宿主 VFS**：搜索路径 = `[请求方 .so 所在目录, RuntimeConfig.library_search_paths...]`

虚拟模块 `Module`：无镜像、无 base、无 TLS；符号表是 `名字 → HostStub`，查到时**按需**
`ThunkTable::add` 生成 thunk VA（同一名字只加一次）。

M4 的虚拟符号集合（只这些）：

| 符号 | 实现 |
|---|---|
| `__errno` | 返回 TLS 里 errno 的地址 |
| `write` | 读 guest 缓冲区 → `::write(fd)`；fd 只允许 1/2 |
| `malloc` | 懒映射的 guest 堆上的 bump 分配器（16 字节对齐） |
| `free` | 空操作 |
| `pthread_once` | 见 §7.1 |

未在表内的虚拟符号 → 打印名字后报未定义。

### 7.1 `pthread_once` 与嵌套 guest 调用

`pthread_once(once_control, init_routine)` 的 `init_routine` 是 **guest 函数指针**，
host stub 必须回调 guest。这是 M4 里唯一一处 M5 前身：

- stub 内 `engine->saveContext()` → `run(entry, return_trap, 0)` → `restoreContext()`，
  与 M0 探针 6 一致
- 嵌套总层数硬上限 **32**（M0 结论），超过直接返回错误，不尝试恢复
- `once_control` 用 guest 内存里的 32 位字：0=未做，1=进行中，2=完成；stub 用宿主 mutex
  串行化（执行锁已经保证单核，这把锁只防同一线程重入）
- M5 的 `Call*Method` 复用同一条 `run` + `save/restore` 路径，不需要重写

为此 `HostCallArgs` 增加一个可选的 `call_guest(GuestVA, args) -> int64_t` 字段，
由 dispatcher 在调用 stub 前填好（它持有 `uc_engine*`）。stub 之外没人用它。

## 8. TLS（M4 不实现，遇到即报错）

> **实测修正（2026-10-28）**：本节的"静态 TLS"方案没有落地。clang 的
> `aarch64-linux-android31` 目标只产 `R_AARCH64_TLSDESC`（`-mtls-dialect=trad`
> 在该 target 上直接报 unsupported），要支持 TLS 就得写 TLSDESC 描述符 +
> guest 侧 resolver 桩，超出 M4 范围。M4 gate 的 fixture 不含 thread_local。
>
> 当前行为：遇到 `R_AARCH64_TLS_TPREL64` / `TLSDESC` / `DTPMOD` / `DTPOFF`
> 一律 `Unsupported`，错误信息带模块名与"需要什么"。真实目标一旦用到 TLS，
> 会在 `loadLibrary` 立刻失败，而不是静默错位。

保留的接口约定：`loadLibrary` 必须发生在第一次 `callFunction` 之前。
理由不变——M3 的 clone 是"adopt guest 传入的 TP"，M4 没有向已存在线程追加
TLS 布局的能力。

`__tls_get_addr` / DTV 动态扩展**不做**。

## 9. 构造与析构

- `loadLibrary` 成功后（依赖全部 `Loaded`）按后序跑 `DT_INIT` 与 `DT_INIT_ARRAY`，
  走 `callFunction` 同一条调用路径
- `DT_FINI` / `DT_FINI_ARRAY` 不跑：M4 没有卸载语义，`RuntimeInstance` 析构即销毁地址空间
- 构造里调用未定义符号 → 按 §5 报错，整个 `loadLibrary` 失败并回滚已映射段

---

## 10. 观测

- 新增 `ModuleEvent`（M2 预留的位置）：`{kind: Load/Resolve/Needed, soname, base, detail}`
  - `Load`：一个模块完成映射
  - `Needed`：一条依赖边（含解析到虚拟模块还是文件）
  - `Resolve`：一个 UND 符号绑定到目标（模块+符号名 / "virtual"）；失败也发一条
- 事件走同步语义通道，与 SvcEvent 同一个 EventBus；`svc.log` 不新增列（模块事件单独
  listener，需要时再考虑落盘格式）
- 未解析符号的 guest 栈 dump 复用 `obs/diagnostic/guest_stack`

## 11. 测试与 fixture

构建（`tests/CMakeLists.txt`，与 blob 同一套 clang）：

```cmake
clang --target=aarch64-linux-android31 -shared -fPIC -nostdlib
      -Wl,--pack-dyn-relocs=none -Wl,-soname,liba.so ...
```

fixture：

| 文件 | 内容 |
|---|---|
| `fixtures/so/libb.c` | 导出 `b_add(x)`（纯计算，带 `.data` 局部变量 → RELATIVE） |
| `fixtures/so/liba.c` | `NEEDED libb.so`；导出 `a_entry(x)` = `b_add(x) + write(...)`；一个 `__attribute__((constructor))` 写标志位 |
| `fixtures/so/liblog_stub.c` | 只为链接期产生 `DT_NEEDED liblog.so`，**不放到运行时搜索路径** |
| `fixtures/so/libmissing.c` | 引用一个谁都不提供的数据符号，用于错误路径 |

`04_so_load` 断言：

1. `loadLibrary("liba.so")` 成功；ModuleEvent 里有 liba、libb、liblog 三条 Load，
   依赖边 liba→libb、liba→liblog，其中 liblog 解析到 `virtual`
2. 构造器在 load 时执行（guest 内存里的标志位 == 1）
3. `callFunction(a_entry(x))` 返回值正确；调用链里 `b_add` 在 libb 内
4. trace 里出现一次 `HostStub` 名为 `write`（证明 JUMP_SLOT → thunk → SVC）
5. `pthread_once` 两次调用只执行一次 init（guest 计数器 == 1）
6. `wrap`/`__cxa_atexit` 之类没实现的符号 → 报未定义（用 libmissing 验证错误信息含符号名）
7. 同一个 `.so` 加载两次 → 同一个 handle，不重复映射

## 12. 不做 / 已知限制

- **打包重定位**：`DT_ANDROID_RELA`（APS2）与 `DT_RELR` 不解析。fixture 用
  `--pack-dyn-relocs=none` 规避。真实 Android `.so` 默认就是打包格式——**这是 M6 的
  必做项**，loader 遇到时给出明确错误而不是静默错位
- 符号版本、IFUNC、`dlopen` 运行期装载、`dlclose`、`RTLD_LOCAL/GLOBAL` 的完整语义
- TLS 全部（见 §8）：TLSDESC 是 Android 唯一可用的模型，M4 不实现
- 未定义**数据**符号（thunk 只能当函数）
- `DT_NEEDED` 的名字到路径只按"同目录 + 配置搜索路径"，没有 `LD_LIBRARY_PATH`
- 虚拟 bionic 是手工符号表，不是真 libc；真 bionic pthread gate 仍等 NDK spike
- 加载期间的构造器若阻塞（futex 等），走的是 M3 已验证的阻塞完成式，不需要特殊处理
