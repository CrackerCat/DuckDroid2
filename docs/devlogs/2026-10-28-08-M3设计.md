## 2. 本体与线程模型

- **Guest 进程** = `RuntimeInstance`：pid、地址空间、thunk 页、EventBus、（M4）loader。
- **Guest 线程** = `RuntimeThread`：

```text
RuntimeThread
  tid
  tls_tp                  # CLONE_SETTLS 传入，runtime 只记录
  clear_child_tid         # CLONE_CHILD_CLEARTID / set_tid_address
  state                   # Created / Runnable / Executing / Blocked / Exited
  std::thread host        # 1:1 宿主线程
  EngineHandle engine     # 1:1 uc_engine
  SvcDispatcher dispatcher
  PendingSyscall pending
  RingBuffer<DiagnosticEvent> diagnostics   # 每线程一个，不加锁
```

- **engine 属于线程**，地址空间属于进程。
- **专用主线程**：`RuntimeInstance::create` 时 spawn 一条宿主线程，专门驾驶主 engine；
  用户线程调用 `callFunction` 只是投递 `(entry, args)` + 等结果。主线程和 clone 出来的线程同构。
- **单核串行**：`execution_mutex` 保证同一时刻只有一条宿主线程在跑 guest 代码。
  宿主线程数 = guest 线程数，但不是并行执行（LDXR/STXR exclusive monitor 是每 engine 一份，
  真并发会坏，决策 02 §4.4）。

## 3. 锁

| 锁 | 内核对照 | 持有范围 |
|---|---|---|
| `execution_mutex`（递归） | “当前哪颗 CPU 在跑” | 驱动循环跨 `uc_emu_start`；阻塞/退出时释放 |
| `instance_mutex` | `mmap_lock` | region 表、线程表、WaitQueue、trace 写入，短暂持有 |
| 每线程 `state_mutex + cv` | `wait_queue_head` | 状态变化 + 唤醒 |

- **为什么不能只用一个锁**：驱动线程持执行锁跑 guest → guest 执行 `mmap` → SVC hook 在同一线程里调
  `memory.map()` → 若 map 也拿执行锁就自锁。内核里 mmap 只拿 `mmap_lock`，不在哪颗 CPU 上是硬件事实；
  我们得把“CPU 所有权”显式化成执行锁。
- 顺序固定：`execution_mutex` → `instance_mutex`。
- 宿主 API（`mapMemory`/`writeMemory` 等）也拿执行锁（递归，同线程重入安全）：
  它要广播到所有 engine，必须保证没有 engine 正在跑。代价是 guest 死循环时宿主 API 会等；
  这是单核模型的必然结果，M3 接受。
- 加锁点：`EventBus::publish` 内部用 `instance_mutex`；trace 的 `id` 分配也在这里。

## 4. clone

### 4.1 arm64 ABI（与 x86 不同）

`clone(flags, stack, parent_tid, child_tid, tls)`，即
`x0=flags, x1=child_stack_top, x2=parent_tidptr, x3=child_tidptr, x4=tls`。
bionic 的 `clone.S` 把 pthread 参数重排成这个顺序后执行 `svc #0`。

### 4.2 flags

接受：

```text
CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD |
CLONE_SYSVSEM | CLONE_SETTLS | CLONE_PARENT_SETTID | CLONE_CHILD_SETTID |
CLONE_CHILD_CLEARTID
```

- 缺 `CLONE_VM` 或 `CLONE_THREAD` = 新进程，M3 不实现 → `-EINVAL`（并在 trace 里记录 unsupported）。
- `CLONE_SETTLS`：`TPIDR_EL0 = x4`。
- `CLONE_PARENT_SETTID`：把新 tid 写到 `*(u32*)x2`（父线程可见）。
- `CLONE_CHILD_SETTID`：把新 tid 写到 `*(u32*)x3`（子线程可见）。
- `CLONE_CHILD_CLEARTID`：线程退出时 `*(u32*)x3 = 0` + futex 唤醒等待该地址的线程。

### 4.3 步骤（全部在 SVC hook 内，持执行锁）

1. 分配 tid（实例内单调递增，主线程 = `config.tid`）。
2. `uc_context_save(父 engine)`；hook 里 PC 已经是 `svc + 4`。
3. 申请 `RuntimeThread`，创建子 engine，重放本进程所有 region，安装 intr hook /
   诊断 hook（绑定到新线程）。
4. `uc_context_restore(子 engine)`。
5. 覆盖：`SP = x1`、`TPIDR_EL0 = x4`（SETTLS）、`X0 = 0`；其余寄存器原样继承。
6. 写 parent_tid / child_tid（若对应 flag）。
7. 记录 `clear_child_tid = x3`（若 CLEARTID）。
8. spawn 宿主线程，进入线程循环；子线程先等执行锁。
9. 父线程 `x0 = 新 tid`，正常返回（PC 不动）。

子线程第一次 `uc_emu_start` 从 `svc + 4` 开始，即 guest 自己在 clone 之后的
`cbz x0` 分支里走“子线程”路径。

### 4.4 引擎结束条件

子线程没有“返回陷阱”，`uc_emu_start(begin=PC, until=0, timeout=0)`：
- `until = 0` 只是“不设结束地址”（Unicorn 把 until 当 exit 地址比较）。
- 线程只能靠 SVC（exit / 阻塞 / exit_group）或 fault 停下来。

## 5. futex 与 PendingSyscall

### 5.1 数据结构

```text
WaitQueue: unordered_map<guest_uaddr, list<RuntimeThread*>>
```

`RuntimeThread::pending` 指向一个 `FutexWaitOp`，它持有进入时构造的 `SvcEvent`
（`seq` 已分配），以及 `uaddr / expected`。

### 5.2 语义

| 调用 | 条件 | 结果 |
|---|---|---|
| `FUTEX_WAIT` | `*(u32*)uaddr != expected` | 立刻 `-EAGAIN`，不阻塞 |
| `FUTEX_WAIT` | 相等 | 入队、pending、Blocked、`uc_emu_stop()`、释放执行锁 |
| 被 `FUTEX_WAKE` 唤醒 | — | `complete(FutexWoke)` → x0 = 0 |
| `FUTEX_WAKE` | — | 摘 ≤ count 个等待者，返回实际唤醒数 |
| timeout 指针非 0 | — | M3 不支持 → `-ENOSYS`（显式暴露） |

- `FUTEX_PRIVATE_FLAG` / `FUTEX_CLOCK_REALTIME` 从 op 里剥掉（`FUTEX_CMD_MASK`），语义按地址匹配。
- `FUTEX_WAIT_BITSET`、PI、robust list、`FUTEX_REQUEUE` 不做。

### 5.3 完成式

- 进入时：`seq = next_seq++`（执行锁下，实例全局计数），构造 `SvcEvent`。
- 阻塞：handler 返回“blocked”，dispatcher 不写 x0、不发布事件。
- 唤醒：waker 在持执行锁时调 `pending->complete(reason)` 得到 x0，存进
  `thread->pending_result`，标 Runnable，通知 cv。
- 线程恢复：自己的驱动循环拿执行锁 → 写 x0 → 清 pending → **发布 SvcEvent**
  （`id = next_id++`）→ 从 `svc + 4` 继续。事件在 guest 恢复的同一执行点发布，
  保证 listener 看到的顺序 = 串行执行顺序。
- 一个 syscall 永远只有一条记录，PC 不回退（决策 02 §3.1）。

### 5.4 线程退出时的等待者

- `exit_group`：所有 Blocked 线程 `complete(ThreadExited)`（x0 = `-EINTR` 或直接丢弃 pending，
  由实例终止路径决定；M3 选丢弃，不再运行）。
- 线程销毁时 pending 直接丢弃，不 complete（决策 02 §3.4）。

## 6. 线程退出与 join

| syscall | 语义 |
|---|---|
| `SYS_exit`(93) | 只结束当前线程。驱动循环停止 engine → state=Exited → 若 `clear_child_tid != 0`：写 0 + futex_wake → 宿主线程结束 |
| `SYS_exit_group`(94) | 结束整个 guest 进程：置实例 stopping → 对所有 engine 跨线程 `uc_emu_stop` → 主线程请求以 `exit_code` 完成 |

- `join` 不需要单独实现：父线程 `futex_wait(&tid, tid)`，子线程 CLEARTID 写 0 并唤醒。
- 子线程的 engine 在 reaper 里销毁（线程对象回收时），宿主线程在实例析构时 join。
- `set_tid_address`(96)：记录 `clear_child_tid` 到当前线程（真实 bionic 启动会调）。

## 7. TLS

- `CLONE_SETTLS`：只写 `TPIDR_EL0`，线程记 `tls_tp`。**不分配、不写 TCB 字段**。
- 运行时需要线程侧数据时，唯一入口是 TCB slot 1：`pthread_internal = *(u64*)(tp + 8)`；
  不再用 `region_base + kThreadOffset` 这种固定偏移（bionic 的 pthread_internal_t 在映射区底部，
  与 tp 的距离随栈大小变）。
- `TlsManager::create()` 只保留给裸 blob 模式（01_tls_read / 03 的主线程）；
  真实 so 的主线程 TLS 由 libc 启动时自己建立，runtime 只 adopt 当前引擎里的 `TPIDR_EL0`。
- `TlsManager::setErrno()` 不再由 dispatcher 调用：errno 是 libc 在 -errno 返回值上做的，
  内核侧（= 我们）不写。

## 8. backend 与内存

- `UnicornBackend` 从“一个 engine”改成“每个 RuntimeThread 一个 engine”的注册表。
- `onMapped/onUnmapped/onProtected/onCodeWritten` 广播到所有 engine；
  新 engine 创建时由 `RuntimeMemory::forEachRegion()` 重放全部 region。
- hook（intr、诊断）按 engine 安装，intr 绑到该线程的 dispatcher，诊断绑到该线程的环。
- 宿主 API 的约束见 §3：拿执行锁后再广播。
- timeout：主线程 `callFunction` 首跑仍用 `default_timeout_us`；子线程与恢复运行传 0
  （Unicorn 的 timeout 每次 `uc_emu_start` 会建一条宿主线程，`uc.c:1036-1040`）。
  已知限制：guest 死循环会挂住 ctest，M3 用 ctest 超时兜底；watchdog 留到后续。

## 9. 观测

- `SvcEvent.tid` = 当前 `RuntimeThread::tid`；`pid` 恒为实例 pid。
- `seq` 与 `id` 的计数移到实例级（执行锁保护），dispatcher 不再自己持有。
- 新增 `ThreadEvent`：`{id, kind=Created/Exited/Blocked/Runnable, tid, parent_tid}`，
  在 clone / exit / 阻塞 / 唤醒时发布；gate 用它断言 created == exited。
- `EventBus`：加 `instance_mutex` 保护 listener 表与发布；
  `delivering()` 改成 **thread-local**（listener 可能跑在任意 guest 线程上，
  M2 的“listener 里调 callFunction 被拒”语义不变）。
- 诊断环移到 `RuntimeThread`；`drainDiagnostics()` 遍历所有线程的环。
- `svc.log` 格式**不变**：首列 `id` 仍单调连续；M3 起 `seq` 可能跨线程交错。

## 10. 调度器骨架

```text
ThreadScheduler（归 RuntimeInstance）
  threads_            # tid -> RuntimeThread*
  wait_queue_         # futex uaddr -> waiters
  execution_mutex_    # 递归
  instance_mutex_     # region/thread 表/trace
  next_tid_, next_seq_, next_id_

主线程循环：
  for (;;) {
    wait: 有 request 或 state == Runnable 或 stopping
    if request: 初始化入口/参数/SP/LR/X29/TP
    while (state == Runnable) {
      lock(execution_mutex)
      state = Executing
      run(engine, PC)
      unlock(execution_mutex)
      case 返回陷阱: 完成 request（x0）
      case Blocked: 等 cv，醒来继续
      case exit_group: 完成 request（exit_code）
      case fault: 完成 request（错误）
    }
  }

子线程循环：同上，去掉 request / 返回陷阱；Exited 即结束。
```

- `callFunction`：投递 request + 等 cv；`delivering()` 为真时立刻拒绝。
- 析构：置 stopping → 跨线程 stop 所有 engine → 通知所有 cv → join 所有宿主线程 → 关 engine。
- `mapMemory` 等宿主 API 与 `callFunction` 可并发调用；`callFunction` 同一时刻只允许一个
  （第二个请求在 instance_mutex 下拒绝或排队；M3 选**拒绝**，保持简单）。

## 11. 测试设计

`03_pthread_join.S`（裸汇编，`-nostdlib`）：

1. 主线程收 `x0 = out buffer`。
2. 循环 100 次：
   - `mmap` 一块 stack（64 KiB）+ 一块 TLS 区（一页；guest 自己初始化 slot 1）
   - 把入口/参数写进约定槽位
   - `clone(flags..., stack_top, &tid, &tid, tls)`
   - 父路径：`futex_wait(&tid, tid)` → 返回 0 表示子线程已 CLEARTID
   - 子路径（x0 == 0）：递增共享计数器、`mrs` 检查 TP、`SYS_exit(0)`
   - 父线程 `munmap` stack/TLS
3. 校验计数 == 100，把汇总写回 out，返回。

断言：

- `clone` 返回的 tid 与子线程 `gettid` 一致；与父 tid 不同
- 每条 `futex_wait` 的返回值 == 0
- `SvcEvent.tid` 覆盖主/子线程
- ThreadEvent：`Created == Exited`（100 对）
- MemoryEvent：map 数 == unmap 数
- trace `id` 连续、`seq` 允许交错

## 12. 不做 / 已知限制

- 不实现“新进程”clone（无 `CLONE_VM|CLONE_THREAD`）
- 不做 futex 超时、bitset、PI、robust list、requeue
- 不做信号（EINTR 只作为将来接口预留）
- 不做抢占：父线程在 guest 里死循环会饿死子线程
- timeout 每次运行会建一条宿主线程；watchdog 留到后续
- 真实 bionic 的 `pthread_*` 不在 M3：等最小 bionic（静态程序 + 最小 loader）跑起来再作为后续 gate
