## 1. 启动顺序

真 Android 的 libc 启动是 libc 自己的 `constructor(1)`：

```text
linker 完成重定位
  -> libc.so 的 init_array[0] = __libc_preinit
       __stack_chk_guard = TLS[slot 5]
       __libc_init_globals()      // __libc_globals 清零 + mprotect
       __libc_init_common()       // environ/progname/pthread_internal_add/properties
       __libc_init_scudo()
       __libc_init_malloc()
       ...
```

因此 M4.6 的开关是 `RuntimeConfig::run_module_initializers = true`（M4.5 已加），
不需要手工调用 `__libc_preinit`。`constructor(1)` 保证它排在所有其他构造器之前。

`__libc_shared_globals()` 在 libc 里只是 `__loader_shared_globals()` 的转发
（`libc_init_dynamic.cpp:176`）。所以这个结构由我们（虚拟 `ld-android.so`）提供。

## 2. `libc_shared_globals` 布局（ROM bootstrap/libc.so 实测）

反汇编依据：

| 偏移 | 字段 | 证据 |
|---|---|---|
| `0x418` | `auxv` | `getauxval` 0x85500: `ldr x8, [x0, #0x418]` |
| `0x450` | `static_tls_layout` | 0x6e890: `ldr x9, [x0, #0x450]` |
| `0x478` | `tls_modules.generation` | preinit 0x56ea8: `add x8, x0, #0x478` |
| `0x480` | `tls_modules.generation_libc_so` | preinit 0x56eac: `str x9, [x0, #0x480]` |
| `0x628` | `set_target_sdk_version_hook` | preinit 0x56f1c: `str x8, [x0, #0x628]` |
| `0x630` | `init_progname` | init_common 0x6a3f8: `ldr x9, [x0, #0x630]` |
| `0x638` | `init_environ` | init_common 0x6a3e4: `ldr x9, [x0, #0x638]` |

`static_tls_layout` 子字段（`bionic_elf_tls.h`，arm64）：

```text
+0x00 offset_                 static TLS 总大小
+0x08 alignment_
+0x10 overflowed_ (bool)
+0x18 offset_bionic_tcb_      = 0（M1 布局 TCB 在块首）
+0x20 offset_bionic_tls_      = 0x200（M1 layout）
```

`offset_thread_pointer() = offset_bionic_tcb_ + 16 = 0x10`，与 M1/M4.5 的 TP 一致。

`tls_modules.generation` 先写 `~0ULL`（与 DuckDroid 一致）；preinit 会把它复制到
libc 自己的 `__libc_tls_generation_copy`。

块大小 0x1000，按页对齐，放在 guest heap（`RuntimeMemory::map`）。

## 3. auxv

按 DuckDroid 的同一组（顺序即内核顺序）：

```text
AT_SYSINFO_EHDR=0, AT_HWCAP=0, AT_PAGESZ=0x1000, AT_CLKTCK=100,
AT_PHDR=0, AT_PHENT=56, AT_PHNUM=0, AT_BASE=0, AT_ENTRY=0,
AT_UID/EUID/GID/EGID=1000, AT_SECURE=0, AT_RANDOM=<16B>, AT_HWCAP2=0,
AT_EXECFN=<progname>, AT_NULL
```

`AT_RANDOM` 同时用于 `__stack_chk_guard`。hwcap 置 0：guest CPU 不宣告可选扩展，
IFUNC 与 libc 的字符串实现都走通用路径（与 M4.5 的 resolver 参数一致）。

## 6. 不做 / 已知限制

- 信号投递只留 no-op，不实现完整语义
- `dlopen/dlclose` 运行期装载不做（M6 前）
- 多实例隔离、warm pool 不做（M7）
- ROM 绑定后换 ROM 必须重新核对 §2 的偏移
- preinit 里的 `__system_properties_init` 允许失败（property 服务不存在），
  错误路径要能被观测到；目标是 malloc/pthread 可用，不是完整 Android 环境

### S3 实现记录（2026-10-28）

- `src/runtime/vfs/`：`File`（`MemoryFile` 生成式伪文件 / `HostFile` 只读宿主文件）、
  `FdTable`（guest fd 从 3 开始；0/1/2 仍是宿主 stdio，不进表）、
  `VirtualFileSystem`（路径规范化、`/proc` 分派、host roots 解析）。
- `/proc/self/{maps,status,auxv,cmdline,comm}` 按打开时快照生成（首次读取时生成并缓存）；
  `maps` 的模块 region 通过 `ModuleRegistry` 解析成加载文件的宿主路径。
- host roots：`RuntimeConfig::filesystem_roots`，每个 root 代表 guest `/`，只读；
  `weakly_canonical` 后检查仍在 root 内，symlink 不能逃逸。
- syscall 面：openat/close/read/write/pread64/lseek/faccessat(+faccessat2)/newfstatat/fstat；
  `struct stat` 按 arm64 内核布局（128 字节）写入。
- 文件 mmap：MAP_PRIVATE 语义即拷贝（读入 guest region，EOF 后补零）；
  可写 MAP_SHARED 需要回写，暂以 EACCES 拒绝。匿名 mmap 路径不变。
- `ErrorCode` 新增 `BadFileDescriptor` / `IsDirectory` / `NotDirectory`，
  由 fs_handlers 映射回 EBADF/EISDIR/ENOTDIR。
- preinit 的 `openat`/`faccessat`/`newfstatat` 全部有答案（属性服务路径 ENOENT），
  未支持 syscall 归零。
- 已知限制：`maps` 显示宿主路径而不是设备上的 `/system/...`；目录 fd/`getdents64` 未实现。

### S5 实现记录（2026-10-28）

- **clone 参数顺序修正（重要）**：arm64 内核 `select CLONE_BACKWARDS`
  （`ROM/kernel/.../arch/arm64/Kconfig`），syscall 顺序是
  `(flags, stack, parent_tid, tls, child_tid)` —— x3 是 TLS、x4 是 child_tid。
  这与 `thread_system.hpp` 旧注释和 M3 裸 blob 里的假设相反（两者自洽，
  所以 `03_pthread_join` 一直通过，但真 bionic 的子线程 TP 落在
  `&thread->tid` 上，`[TP+8]` 为 0 直接崩）。证据：`__bionic_clone.S`
  直接原样 `svc`，参数在 x3/x4；修正 handler 与 blob。
- 主线程 TP 由 libc 接管：`__libc_init_main_thread_final` 与每个
  `pthread_create` 都用 `__set_tls`（纯 `msr tpidr_el0`，无 syscall）更换。
  scheduler 在每次 run 结束回读 TPIDR_EL0 存回 `RuntimeThread::tls_tp`，
  否则下次 `callFunction` 会把 TP 恢复成 preinit 前的旧块。
- `StaticTlsLayout` 按 bionic `finish_layout` 语义发布：总大小向上取整到
  最大对齐（至少 16），否则 `static_tls = end - guard - size` 可能不对齐，
  新线程的 TP/模块 TLS 一起错位。
- 新线程路径：libc 自己 `mmap(PROT_NONE|NORESERVE)` → `mprotect` →
  写 pthread_internal_t/TCB → `clone`；runtime 只 adopt TP/栈/context，
  不代为分配。gate 里 10 次 create/join 计数正确，两个线程并存时
  `/proc/self/status` 的 `Threads` 为 3，errno 地址每线程独立。
- `libeleven.so`（真实闭包 liblog/libm/libdl/libc++ + ROM libc）可加载，
  `JNI_OnLoad` 可解析；调用它需要 JavaVM，属 M5。
- 已知限制：`__libc_shared_globals()->tls_modules` 仍为空表，因此新线程的
  模块 PT_TLS 初始化镜像不会被 `__init_static_tls` 复制（当前 libc 唯一
  PT_TLS 是 gwp_asan；libc++ 无 PT_TLS）。futex 仍无超时/WAIT_BITSET/PI。

新增的调试设施：Unicorn 未映射访问钩子（打印 type/address/size/pc），
在定位 scudo 的 tagged 写时直接给出了 `0x02...` 地址。
