## 1. 范围

### 做

1. **指令级 trace**：在指定 guest 地址区间内产出 `code.log` / `bl.log` / `rw.log`，
   严格沿用 QBDI 四件套的列结构、行号语义、hexdump 和 JSON 约定。
2. **地址 hook**：给一个绝对 guest 地址注册回调；回调在指令执行前同步运行，
   可以读/写通用寄存器与内存、改 PC，用来做观测和故障注入。
3. 二者可以同时启用。hook 在 trace 的 PRE 采样之前运行。

### 不做

- `mem/` 内存快照（不 dump 完整内存）。
- bionic / linker / 其他模块的**指令**：trace 区间外的指令不进 `code.log`，
  但它们触发的访存也不进 `rw.log`。
- NEON/Q/D/S 等向量寄存器：这一轮不记录、不写入。
- 生产构建不带 capstone。指令级 trace 由 `DUCKEMU_ENABLE_TRACE` 显式打开。
- 回调里的动态 hook 注册 / 卸载；回调里调用 `callFunction`。

## 2. 探针结果

探针代码在 `code/tools/spike/unicorn_spike.cpp` 的 Probe 10/11；capstone 行为用
`/tmp` 下的独立小程序逐条核对（不进入仓库构建）。

### 2.1 Probe 10：`UC_HOOK_CODE` 写 PC 能重定向

| 场景 | 结果 |
|---|---|
| 同一直线块内改 PC（跳过两条指令） | `x1`/`x2` 保持 0，`x3 = 0x13`，**重定向成功** |
| 跨可执行页改 PC | `x1 = 0`，`x4 = 0x44`，**重定向成功** |
| 回调次数 | 只命中被 hook 的地址一次；被跳过的地址不再触发 code hook |

结论：`HookContext::setPc()` 可以直接落地。skip / replace 不需要 SVC 补丁，
也不需要 stop-resume。

### 2.2 Probe 11：回调顺序与 SVC 重放

实测事件序列（`ldr` / `str` / `svc`）：

```
code 0x1000c
read 0x20000  pc=0x1000c
code 0x10010
write 0x20008 pc=0x10010
code 0x10014          <- SVC 的 code hook 先触发
intr 0x10018          <- 然后才是 INTR；hook 里 PC = svc + 4
code 0x10018          <- 恢复后执行 svc+4
```

- code hook **先于**该指令的 mem hook。
- **mem hook 里的 PC 就是当前指令地址**（上表 `pc` 列）。这是 trace 判断
  “这次访存是不是区间内指令产生的”的唯一依据。
- SVC **会触发 code hook**，顺序在 INTR 之前。
- INTR 里 `uc_emu_stop`，宿主从 `svc + 4` 续跑：SVC 的 code hook 与 INTR
  都**不重放**。

### 2.3 capstone 操作数分析

capstone 5.0.9。对 `stp/mov/movk/adrp/ldrb/strb/ldr/ldr post-index/blr/bl/
paciasp/autiasp/svc/ret` 逐条核对：

- `cs_insn.detail->regs_read/regs_write` **只含隐式寄存器**，显式操作数不在里面。
  读/写集合必须从 `arm64.operands[].access` 推导：
  - `access & CS_AC_READ` → 读；`access & CS_AC_WRITE` → 写；
  - `ARM64_OP_MEM` 的 `base`/`index` 默认是读；
  - `arm64.writeback` 为真时，`mem.base` 还要加进写集合（`stp ... [sp,#-0x60]!`、
    `ldr x1,[x0],#8`）；
  - 立即数、系统寄存器操作数跳过。
- 隐式寄存器只补这几类：
  - `bl/blr/blra*`：写 LR；
  - `ret/retaa/retab`：读 LR；
  - `paciasp/autiasp/pacibsp/autibsp`：读/写 LR，读 SP（按 capstone 的隐式表）；
  - `svc`：**不写任何 GPR**（capstone 给 `regs_write=lr` 是错的，必须过滤）。
- 名字映射：`fp → FP`、`lr → LR`、`sp → SP`、其余大写（`x9 → X9`、`w10 → W10`）。
- `insn` 文本 = `mnemonic + " " + op_str`，tab 替换为空格，外层加双引号。
  **和 QBDI（LLVM MC）不会逐字一致**，例如 `adrp x9, #0x1000` vs
  `adrp x9, #1449984`。两份 trace 按地址对齐比对，不做文本 diff。

## 3. trace 语义

### 3.1 区间

- 用户给 `[begin, begin + size)`，必须完整落在一个已加载模块内。裸 blob /
  JIT 区域没有 `Module` 时，回落到包含它的 `Region`，`offset` 相对 region base。
- `code.log` 只写 PC 在该区间的指令；`rw.log` 只写这些指令产生的访存；
  `bl.log` 写这些指令里 **目标跳出区间** 的 `bl/blr/blra*`。
- 模块基址用于 `offset` 列：`address - module.base`。区间跨越模块边界时
  `startInsnTrace` 直接报错。
- `InsnTraceOptions::stop_at_return`（QBDI nested-VM 结尾）：在区间内第一条
  指令处捕获进入时的 LR，PC == LR 时停止记录。`begin/size` 只作为 hook 覆盖
  （通常是目标模块），不再用函数大小常量；分析 runner 走这个模式，CLI 只给
  `--trace DIR`。
- 一条指令 `bl` 到同模块但区间外的函数：进 `bl.log`（符号会解析成
  `模块名!0x偏移` 或最近的导出名）。这样才能看到“目标函数调了谁”。

### 3.2 行号与多线程

- 每个 trace 会话从 `0` 开始，跨所有 engine 全局递增，连续无空洞。
- 文件一次会话只 open 一次（`O_TRUNC`），会话结束 flush/close。
- 多线程：实例执行锁保证同一时刻只有一个 engine 在执行，行号天然有序。
- **三文件保持 7 列/原格式，不新增 `tid` 列，也不往 `note` 里塞 tid。**
  线程归属写在同目录的 `threads.tsv`：

  ```
  <hex line>\t<0x tid>
  ```

  只在执行线程切换时追加一行；解析端按“最后一条 ≤ 当前 line 的记录”继承。
  这样 QBDI 生态的解析器不需要改。

### 3.3 code.log

格式串与 QBDI 完全一致：

```
%llx\t0x%-12llx\t0x%-8llx\t"%s"\t%-28s\t%-28s\t%s
```

- 第 5 列是 PRE 值，第 6 列是 POST 值。
- PRE 在指令执行前读；POST 在下一条指令的 code hook 或本次 run 结束时读。
- 寄存器名全大写；值 `0x` 前缀小写十六进制；无读写时 `{}`。
- SVC 行立即写（不进入 pending），`writes` 为 `{}`，note 写入 syscall 注解：
  - 真 syscall：`{"syscall":"read","args":["0x1",...]}`
  - 未知号码：`{"syscall":"syscall_<n>","args":[...]}`
  - thunk（`svc #>=0x8000`）：`{"host":"0x<index>","args":[...]}`（扩展）
- 其余行的 note 恒为 `{}`。

### 3.4 bl.log

```
%llx\t0x%llx\t%s
```

- 触发点：区间内 `bl/blr/blra*` 的 code hook。
- 目标：`bl` 取立即数；`blr` 取目标寄存器的 PRE 值。
- 符号降级：宿主 thunk 名（`JNIEnv::NewStringUTF`、导入函数名等）→
  模块内最近的前置 `STT_FUNC` 符号 → `模块名!0x偏移` → 裸 `0x地址`。
  thunk 名来自 `ThunkTable`：目标落在 thunk 页且 8 字节对齐时按
  `(target - base) / 8` 取 `nameOf(index)`。
- 索引行后跟目标地址 `- 0x10` 起的 hexdump（0~3 行，规则同 QBDI）。

### 3.5 rw.log

```
%llx\t%s\t0x%llx+0x%llx
```

- `line` 用当前指令的行号；`r`/`w` 由 Unicorn 的 mem hook 给出。
- **第三列故意写成 `访问地址+0x0`**：和 QBDI 实测数据保持一致，保住
  `rg '\tw\t0xADDR'` 这类按绝对地址搜索的用法。`base±offset` 的分解这一轮不做。
- 访问地址按 QBDI 的做法 `& 0xFFFFFFFFFFFF`（去 TBI tag）。
- 同一行号可有多条；行号单调不减。
- 只有 `mem hook 里的 PC` 等于当前指令地址时才记录——这是排除区间外
  （libc/linker）访存的依据。
- **访存先缓存、到该指令的 POST 阶段再落盘**：Unicorn 的写 hook 在存储提交
  前触发，立即写盘会让 `w` 条目的 hexdump 是写前内容；缓存到 POST 后
  `hexdump` 才是写后内容，和 QBDI `getInstMemoryAccess()` 一致。
  每条指令最多缓存 8 条访存（QBDI 实测最大 4）。

### 3.6 hexdump

```text
%08llx: xx xx ... (16 字节，每字节后一个空格) |ascii| 
```

- 从 `addr - 0x10` 起读最多 `0x30` 字节；地址 `< 0x10` 时从 0 起。
- 读不到（未映射 / 无读权限 / 跨洞）就按实际读到的字节数出行：
  满 3 行、部分行、或整段 hexdump 消失。
- 末行缺字节：字节区补 `"   "`，ASCII 区补空格。
- 读内存走 RuntimeMemory 的区域表，不用裸 `memcpy`，不踩宿主 SIGSEGV。

### 3.7 预算与截断

- `max_instructions`（默认 0 = 不限）：达到后**停止记录**，不停止 emulation。
- 截断不写注释行（格式里没有注释语义），由宿主日志留一条 WARN。

## 4. 地址 hook 语义

### 4.1 注册与触发

- API 只接受**绝对 guest 地址**；必须 4 字节对齐且落在可执行区域。
- 回调在每次执行到该地址时、**该指令执行前**同步调用。
- 顺序：用户 hook → trace 的 PRE 采样 → 指令执行。
  因此 hook 写寄存器/内存后，trace 记录的是 guest 实际看到的值。
- 回调里 `setPc()` 生效（Probe 10）；改了 PC 就跳过本指令的 trace 记录，
  从新 PC 继续。
- 所有 engine（包括之后 clone 出来的线程）都会装上 hook。

### 4.2 API

```cpp
struct HookContext {
    uint32_t tid;
    uint64_t address;
    uint64_t hit_count;   // 本次顶层调用里第几次命中（1 起，跨线程累计）
    uint64_t lr, sp;
    std::array<uint64_t, 8> x;

    uint64_t readX(int n) const;              // X0..X30（X29=FP，X30=LR）
    void     writeX(int n, uint64_t v);
    uint32_t readW(int n) const;
    void     writeW(int n, uint32_t v);
    uint64_t readSp() const;
    void     writeSp(uint64_t v);
    Result<std::vector<uint8_t>> readMemory(uint64_t va, size_t n) const;
    Result<void> writeMemory(uint64_t va, const void* p, size_t n);   // 检查 PermWrite
    Result<void> forceWriteMemory(uint64_t va, const void* p, size_t n); // 只要求已映射
    Result<void> setPc(uint64_t va);
};

Result<uint32_t> addAddressHook(GuestVA address, std::function<void(HookContext&)> hook);
bool removeAddressHook(uint32_t id);
```

- `x`/`lr`/`sp` 是 hook 开始时的快照；`readX` 读实时值。
- `hit_count` 在每次顶层 `callFunction` 开始时归零。
- `forceWriteMemory` 用于把故障打进 `.rodata` 表；仍然要求地址已映射。
- 回调在 Unicorn 的 C 帧里运行：不能抛异常（会被捕获并记 ERROR），
  不能调用 `callFunction`，不能在回调里增删 hook。注册/删除都在宿主侧、
  下一次调用之前完成。

### 4.3 白盒 AES / DFA 用法

- 轮次选择：`ctx.hit_count`。
- 状态读写：`readMemory` / `writeMemory`（目标状态通常在可写内存）。
- 查表故障：`forceWriteMemory`。
- 寄存器故障：`writeX` / `writeW`。
- 改“某条指令的结果” → hook 下一条实际执行的地址，而不是这条本身。

## 5. 实现结构

```text
runtime/observer/trace/
├── insn_decode.{hpp,cpp}     # capstone 解码缓存 + 操作数分析（仅 TRACE 构建）
├── insn_trace.{hpp,cpp}      # 三文件 sink、行号、threads.tsv、hexdump（仅 TRACE 构建）
├── insn_trace_stub.cpp       # 未启用 TRACE 时的工厂，返回错误
└── buffered_file.{hpp,cpp}   # 1 MiB 缓冲写入器（移植 RawMemoryLogger 思路）

runtime/observer/hook/
├── hook_context.{hpp,cpp}    # HookContext 的实现（读寄存器/内存、写、setPc）
└── address_hook.hpp          # AddressHook / HookContext 的公共声明

runtime/backend/unicorn/
├── unicorn_engine.{hpp,cpp}  # 增加 trace 的 code/mem hook、run-end 回调
├── unicorn_backend.{hpp,cpp} # hook 注册表、trace sink 生命周期、跨 engine 安装
└── unicorn_hooks.cpp         # 新增 trace/hook 的 C 回调入口
```

- **构建开关**：`-DDUCKEMU_ENABLE_TRACE=ON`。开启时用 pkg-config 找
  `capstone >= 5`，只给 `duckemu_runtime` 链接；关闭时编译 `insn_trace_stub.cpp`，
  `startInsnTrace` 返回“未启用”错误。hook 不依赖 capstone，始终编译。
- **backend 负责**：hook 表、每个 engine 的 `EngineState`、trace sink 指针、
  新 engine 的 hook 安装。`EngineState` 作为 Unicorn 回调的 `user_data`。
  `createInsnTrace(options, memory, modules, thunks)` 额外拿 `ThunkTable`，
  用来把 thunk 页里的 `blr` 目标符号化成宿主函数名。
- **`startInsnTrace` / `stopInsnTrace`** 不能在 hook 回调里调用（会改正在
  运行的 engine 的 hook 链）；backend 用 `inHookCallback()` 拒绝。
- **scheduler 负责**：每次顶层 `callFunction` 开始时重置 hook 命中计数。
- **engine 负责**：`run` 返回后调用 run-end 回调，flush pending 的 POST。

## 7. 已知限制

- NEON/Q/D/S 寄存器不记录、不写入。
- `insn` 文本与 QBDI 的 LLVM MC 不完全一致。
- `rw.log` 的 `base±offset` 分解保持 `+0x0`，和既有数据一致。
- 区间外的代码不插桩，所以看不到 libc 内部指令；这也意味着
  “区间外代码调回区间内”会产生新的行号，但区间外那一段没有行。
- 阻塞式 syscall 的 x0 由 dispatcher 在恢复时写入；SVC 行本身不记录 POST。
- 一条指令最多缓存 8 条访存；超过的部分丢弃（QBDI 实测最大 4）。
- 线程退出后 sink 里该 engine 的 pending 条目不会立即回收；引擎 id 不复用，
  下一次 `startInsnTrace` 建新 sink 时随 sink 一起释放。

### 8.4 真实目标

libeleven（`libeleven.so+0x40cb4`，native 入口）：

```
./build-trace/user_code/duckemu_libeleven_case --trace /tmp/le_insn 1
```

分析 runner 只有一个 `--trace DIR`：`svc.log` 写 `DIR/svc.log`，指令 trace 写
`DIR/insn/`。范围不是 CLI 参数：`begin/size` 只作为 hook 覆盖（目标模块），
trace 在区间内第一条指令处捕获进入时的 LR，**PC == LR 时停止记录**——这是
QBDI 嵌套 VM 的结尾，不猜函数大小，也没有调用栈跟踪或“挂起”。执行是直线流。

- 日志头：`insn trace: libeleven.so+0x0 size=0xc9000`（hook 覆盖模块）；
  `code.log` 7,646 行，首条是 native 入口 `+0x40cb4`，最后一条是它的
  `ret`（`+0x40ed0`）；同模块 callee 也在直线流里。
- `code.log` 的 `offset` 是模块内偏移，`insn`/reads/writes 与 QBDI 同构。
- `bl.log` 只剩真正跳出模块的调用（JNIEnv/libc），4 行。
- `rw.log` 14,488 行/1.8 MiB；`threads.tsv` 为 `0\t0x1`。
- 一次 data(1) 约 1.4 s（含实例创建/加载），插桩开销对分析场景可接受；
  这不是大目标吞吐基准。

### 8.5 京东 libjdg

`Bridge.main` 的注册入口是跳板（`br`/`b` 到函数表里的 handler），真实签名流跨
整个 `.text`，包括入口以下的函数；连续的函数区间会漏掉大部分代码。JD runner
因此用 `moduleRange(handle)` 作为代码内范围；CLI 仍只有 `--trace DIR`，指令
trace 只覆盖 sign 调用（init 在 trace 开始前）。

hook 覆盖同样是模块范围；trace 在第一条实际执行的模块指令（`+0xa3858`）处
捕获 LR，到 LR/调用返回结束。

实测一次 `main(101)`：

| 文件 | 行数 | 大小 |
|---|---:|---:|
| `insn/code.log` | 1,171,888 | 129 MiB |
| `insn/rw.log` | 2,155,668 | 132 MiB |
| `insn/bl.log` | 1,708 | 107 KiB |
| `svc.log` | — | 74 KiB |

合计约 261 MiB，耗时约 5.2 s。`code.log` 是 sign 期间模块内实际执行的指令；
`bl.log` 是跳出模块的 JNIEnv/libc 调用。libeleven 与京东的 hook 覆盖都由目标
代码选择，trace 结尾统一是进入时的 LR。
