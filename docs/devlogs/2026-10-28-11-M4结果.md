## 3. 关键实现决定与设计的差异

1. **TLS 不实现。** 设计 §8 原计划做静态 TLS + `TLS_TPREL64`。实测 clang 的
   `aarch64-linux-android31` 只产出 `R_AARCH64_TLSDESC`（`-mtls-dialect=trad` 对该
   target 报 unsupported），要支持就得写 TLSDESC 描述符和 guest resolver 桩。M4 改为
   遇到 TLS 重定位立即 `Unsupported`，错误信息说明缺什么。**这是与路线图
   "TLS_* 重定位"一条的明确偏差**，留给需要 TLS 的真实目标（M6）。
2. **`pthread_once` 需要 host→guest 回调，M4 提前落了一条最小调用桥。**
   `HostCallArgs` 增加 `call_guest` 与 `thread_pointer` 两个字段，由 dispatcher 填。
   `call_guest` 在同一个 engine 上嵌套 `uc_emu_start`，前后 `uc_context_save/restore`，
   总层数硬上限 32（M0 结论）。这是 M5 `Call*Method` 的同一条路径，M5 不再重写。
3. **加载与构造器分两段。** `ModuleLoader::load()` 只做映射/重定位，不跑 guest 代码；
   `RuntimeInstance::loadLibrary` 先持执行锁加载，**释放锁后**再逐个
   `callFunction(initializer)`。否则主 guest 线程拿不到执行锁，构造器会永久阻塞。
4. **虚拟模块优先于文件系统。** `DT_NEEDED` 先查虚拟表（按 soname 精确匹配），再查
   VFS。测试里 `so-runtime/liblog.so`、`so-runtime/libc.so` 故意放的是非 ELF 垃圾，
   一旦顺序反了立刻失败。
5. **虚拟 `write` 独立实现，不复用 SVC handler。** SVC 的 `sysWrite` 需要
   `SyscallContext`（线程、内存、线程表），thunk stub 只有 x0..x7；M4 让虚拟 `write`
   自己读 guest 内存再调宿主 `::write`（fd 仍只允许 1/2）。语义与 SVC 版本一致，代价是
   两份 10 行代码。
6. **`malloc` 是缩水版**：懒映射 1 MiB guest 堆 + 16 字节对齐 bump 分配，`free` 空操作，
   堆用满返回 NULL（不 `mmap` 扩容）。够 gate 用，真实目标要换。
7. **`ModuleEvent` 只发三类**：`Load`（成功映射，虚拟模块 detail=`virtual`）、
   `Needed`（依赖边，含失败原因）、`Resolve`（仅未定义符号，`-> virtual` 或失败）。
   模块内部的 RELATIVE/GLOB_DAT 不发事件，避免噪声。
8. **失败回滚只回滚当前模块。** 依赖已经加载成功的保持映射；它们的构造器如果还没跑，
   会被 `takeInitializers()` 丢弃（不跑），实例仍可用。这与 ld.so 的行为不同，记在
   §5。

## 4. 踩到的坑

### 4.1 `PT_DYNAMIC` 存了循环内局部变量的地址

第一版把 `Elf64_Phdr *dynamic_header = &program;` 存下来（`program` 是 for 循环里的
局部变量），出循环即悬垂。症状不是崩溃，而是**动态段全空**：没有 `DT_NEEDED`、没有
符号表、没有重定位，模块用一个"只有 PT_LOAD"的空壳加载成功，`lookupSymbol` 报
`does not export 'a_entry'`。改成按值拷贝 phdr 后正常。

教训：解析器的失败模式是"空但合法"，gate 断言必须覆盖符号/依赖/重定位三类内容，
只断言"load 成功"会漏掉。

### 4.2 `next_base_` 没在构造器里初始化

头文件里从 `uint64_t next_base_ = 0x60000000;` 改成 `uint64_t next_base_;` 后忘了加进
初始化列表，模块被映射到 0 号地址。表现同样是"加载成功但 base 是 0"。

### 4.3 clang `-O1` 会折叠只写全局量的构造函数

```c
int g;
__attribute__((constructor)) static void ctor(void) { g = 1; }
```

`-O1` 下 clang 认为"进 main 前把 g 置 1"等价于 `.data` 初值，于是**整个 `.init_array`
条目被删掉**，`-O0` 才保留。fixture 的构造器改成调用依赖模块的函数
（`g_ctor_ran = b_add(1)`），优化器无法折叠。用 `used, noinline` 也救不回来。

### 4.4 undefined 符号在 clang 里是 `STT_NOTYPE`

clang 对"只有声明、没有定义"的函数，`st_info` 类型是 `NOTYPE`，不是 `FUNC`（GCC 是
`FUNC`）。所以 loader **不能**用符号类型区分函数/数据：M4 的规则是"未定义且解析不到"
才看类型，`OBJECT` 报错（thunk 不能当数据指针），其余按函数处理。

### 4.5 Android 默认打包重定位

`--target=aarch64-linux-android31` 的 lld 默认产出 `DT_ANDROID_RELA`（APS2 压缩格式）
和 `DT_RELR`，都不是标准 RELA。fixture 用 `-Wl,--pack-dyn-relocs=none` 规避；loader
检测到这两类 tag 直接报错并提示重建参数。**真实 Android `.so` 默认就是打包格式**，
M6 必须实现解析，否则连加载都进不去。

### 4.6 大页对齐

clang 给 Android 默认 `-z max-page-size=0x4000`（16 KiB），PT_LOAD 的 `p_vaddr` 与
`p_offset` 只在 `p_align` 内同余，不是页对齐（例如 `p_vaddr=0x439c`）。映射必须按
"页下取整的 vaddr ↔ 页下取整的 offset"对拷，不能假设 `vaddr == offset`。

## 5. 已知限制

- **打包重定位不解析**（§4.5）；`DT_RELR` 同样不支持。
- **TLS 全部不支持**：`TPREL64` / `TLSDESC` / `DTPMOD` / `DTPOFF` 一律加载失败。
- **符号版本被忽略**：`DT_VERSYM`/`DT_VERNEED` 不读，按名字匹配。真实 libc 的
  `LIBC`/`LIBC_N` 版本要求不会生效。
- **无 IFUNC、无惰性绑定、无 interposition**：定义在本模块的符号直接用本地地址，
  不检查全局覆盖（`LD_PRELOAD` 语义不成立）。
- **`DT_NEEDED` 只按"模块目录 + 配置搜索路径"找**，没有 `LD_LIBRARY_PATH`，
  也没有"文件名 → soname"的别名表。
- **失败回滚不级联**：依赖已加载就保留，父模块卸载不影响它们。
- **`malloc` 不扩容**，`free` 是空操作；`write` 只接受 fd 1/2。
- **没有卸载**：`dlclose`/`DT_FINI`/`DT_FINI_ARRAY` 都不做，析构即销毁地址空间。
- 构造器里若调用会阻塞的 syscall，会走 M3 的阻塞完成式；这条路径没有专门测试。
- 虚拟 bionic 仍是手工符号表，不是真 libc；真 bionic pthread gate 仍等 NDK spike。
