# 得物 6.1.5.10 接入：libszstone.lf、/proc 快照与 CFI shadow

> 日期：2026-10-30
> 目标：`com.shizhuang.stone.main.SzSdk.lf([BZZZ)[B` 在当前 main 上跑通，
> 按 `ENVIRONMENT.md` 把设备画像、系统属性与文件快照收进
> `code/user_code/szstone_case/`，并留一个可复现的 gate。

## 1. 结论

- `libszstone.so`（UPX 打包、DT_INIT 原地自解包）正常加载，10 个
  `RegisterNatives` 全部绑定；lf 正常返回，`JniEvent = 0`。
- 输入面只有四路（外加时钟/随机）：文件 IO、syscall、JNI、`ro.*` 属性。
  设备快照与属性画像固定后，**注入 wall clock 即可逐字节复现**。
- 本次新增的 runtime 面有两个：`/proc` 快照优先回落（含
  `/proc/<pid>/x` → `self/x`、`/proc/self/mem`）和 **CFI shadow 初始化**。
  后者不是可选项：没有它，任何经过 CFI 检查的间接调用都会在 libdl 的
  `__cfi_slowpath` 里读地址 0。

## 2. 迁移与整理

- 代码从 `environment/szstone_case` 迁入 `code/user_code/szstone_case/`，
  并接上 CMake target、worker registry（app id `szstone`）与 gate。
- `main.cpp` 与 `plugin.cpp` 里重复的 hex / `z` 解析合并为
  `szstone_codec.hpp`；两边都改走 `invokeLf(instance, blob, z)`，参数布局只写
  一处。
- 设备属性写成项目侧的 `szstone.properties`（见 §4），不再依赖环境变量或
  全量 `prop.default`。

## 3. 崩溃定位：CFI shadow

迁移后第一次运行崩在：

```text
guest read unmapped: address=0x3006 size=2 pc=0x600f91b8
x8=0x3006
```

`DUCKEMU_LOAD_TRACE` 显示 `pc` 属于 `libdl.so`（base `0x600f8000`，
offset `0x11b8` = `__cfi_slowpath`）。它执行：

```text
x9 = shadow_base_storage
ldrh w8, [x9 + (target >> 17)]
```

`shadow_base_storage` 是 0，于是从地址 0 取表项，`target` 是 libc 的
`__socket`（`0x600c7760 >> 17 = 0x3006`）。

真 Android 的 linker 在加载 libdl 后调用 `__cfi_init(shadow_base)`。
虚拟 linker 之前只把 `__cfi_init` 当成普通导出符号，从未调用。
现在 `RuntimeInstance::loadLibrary` 在依赖加载完成后：

1. 查 `__cfi_init`；存在则映射 64 MiB 的零表（覆盖 8 TiB 以下的全部地址，
   模块区 `0x60000000` 的索引只有 `0x30000`）；
2. 通过 scheduler 调一次 `__cfi_init(base)`；
3. 每个实例只做一次。

零表项会走 `__loader_cfi_fail`，而虚拟 ld-android 把这个符号绑成返回桩，
所以检查被跳过而不是 abort。真实 linker 在这里会终止；需要严格 CFI 时再
把 shadow 按模块代码区间填 1。

## 4. `/proc` 快照与属性

`/proc` 的语义定为“**文件根里有就用快照，没有才合成**”，这样设备进程的
`maps` / `status` 会被 native 读到，长度与真机一致；需要实例级视图时不要把
这两份放进根。`/proc/<pid>/x` 与 `thread-self/x` 映射到快照的 `self/x`；
`/proc/self/mem` 是可打开的空文件。

属性走框架自己的 `/dev/__properties__` 镜像（真 libc 自己解析），不再用
分支上的 `__system_property_get` 覆盖。全量 `prop.default` 有 1098 个键，
超过 128 KiB 属性区，因此 `szstone.properties` 只保留 lf 实际查询的 26 个
有值键，外加少量设备标识键，使其与 `assets/root` 的 Mi 8 快照一致。快照里
不存在的键（`ro.kernel.qemu` 等）不写，真机也返回空。

## 5. 长度与可复现性

默认调用是 `z=(1,1,1)`，与真机 sk 注册的 `lf(blob, true, true, true)` 一致。

| 环境                                                                  | 长度                     |
| --------------------------------------------------------------------- | ------------------------ |
| 设备快照 + 属性，宿主时钟                                             | 3199                     |
| 同上，注入 `--wall-time-ns` + `--monotonic-time-ns` + `--random-seed` | 3183，且跨进程逐字节相同 |
| 同上再挂真机 APK（`call_0` 抓包配置）                                 | **3263**                 |

旧文档/gate 里的 3215 是另一份属性画像的结果：当时
`gsm.version.baseband` 还在表里，配合 `z=(1,1,1)` 与注入时钟，不挂 APK
正好是 3215。`call_0` 证明真机那次调用看不到 baseband（空值），把它去掉
后挂 APK 正好对上抓包的 3263；所以 3215 不是错误，只是对应另一次抓取。

### 与 `call_0_3263.req.txt` 对拍

`logs/capture/call_0_3263.req.txt` 的 body 是 `base64url(lf_out)`，解码为
3263 字节（与 `lf_out_0_3263.bin` 逐字节相同）。把完整 APK 按画像的
`dadir` 路径放进 guest 根后运行：

```bash
APK_ROOT=/tmp/szs-apk-root
mkdir -p "$APK_ROOT/data/app/~~jKTCowhdea931IMmF_a-DA==/com.shizhuang.duapp-3R6fyRkBVCZKmrfOBdhqrA=="
ln /path/to/du.apk \
  "$APK_ROOT/data/app/~~jKTCowhdea931IMmF_a-DA==/com.shizhuang.duapp-3R6fyRkBVCZKmrfOBdhqrA==/base.apk"

./build/user_code/duckemu_szstone_case --root "$APK_ROOT"
# lf in=2980 z=(1,1,1) out=3263
```

实测：长度与抓包一致；尾部有 336 字节的加密区块与抓包相同（同一 AES 块
对齐），但 nonce 与真机实际耗时不同，字节不会逐位相等。注入 wall clock
会让长度变成 3247——注入是冻结时钟，和真机的流逝时间语义不同，所以对拍
抓包时用宿主时钟。

## 6. gate 与已知差距

`07f_szstone_plugin`：两个全新实例，相同墙钟/单调钟/随机种子，各以
`z=(1,1,1)` 调用一次 `lf`；断言 body 非空、长度 3183、`JniEvent=0`、两次
body 逐字节相同。单调钟必须一起钉住：lf 有一部分输出包含耗时字段，只钉
墙钟时两个实例仍会不同。

- 与真机的 3263 仍差一次 APK 挂载：完整 APK 不入库，`--root` 手动挂。
- 字节不等于 `lf_out.bin`：nonce 与抓取时不同；要逐字节需要固定随机源并用
  同一次调用的进程快照。
- `fork/vfork` 仍不支持：libszstone 的 `popen` 探测会失败，native 走回退
  路径。它不影响结果，但这是“没有子进程”而不是“子进程成功”。
- clone 不支持时返回 `EINVAL`；试过 `ENOSYS` 不改变本目标的路径，已回退。
