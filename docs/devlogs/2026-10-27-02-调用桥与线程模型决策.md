# 2026-10-27 调用桥与线程模型决策

本文件回答三件事：guest/host 到底是什么、guest 怎么调到 host、多个 guest 线程怎么跑。
所有结论基于 `code/third_party/unicorn`（API 2.1）源码；拿不准的进 M0 探针（§5）。

---

## 1. 术语：host 与 guest

- **Host**：你写的 C++ 程序。WorkerProcess、RuntimeInstance、Memory、JniStub、以及 Unicorn 库本身，都跑在 x86_64 Linux 上。
- **Guest**：Unicorn 里那个 ARM64 世界——目标 `.so` 的指令、寄存器、地址空间。它是**数据**，不是线程。

`RuntimeInstance` 是"装着 guest 世界的 host 对象"。worker 和 runtimeinstance 都在 host 侧，不是 host 与 guest 的区别。

## 2. Guest → Host 调用桥

### 2.1 为什么需要

guest 里的 ARM64 代码执行到 `bl malloc`、`bl write`、或 `env->NewStringUTF` 时，真实 Android 上会跳进 `libc.so` / `libart.so` 的 ARM64 实现。我们不加载这些库（那等于要模拟内核），实现必须在 host 的 C++ 里。问题是：**控制权怎么从 ARM64 代码交到 C++，再交回去？**

### 2.2 方案：SVC 陷阱 + guest 内 thunk 页

RuntimeInstance 初始化时，在 guest 地址空间映射**一页只读 thunk 页**。每个需要 host 实现的函数分配一个 index，thunk 内容是：

```asm
svc #(0x8000 | index)   ; index < 0x7fff
ret
```

调用方（guest）按 AAPCS64 已经把参数放在 x0~x7 / 栈上，因此 **thunk 不需要搬运参数**。

分发规则：

| SVC imm16 | 含义 | 号/参数位置 |
|---|---|---|
| `0` | Linux syscall | syscall 号在 x8，参数 x0~x5 |
| `0x8000..0xFFFF` | host stub | index = imm & 0x7fff |

所有"guest 调 host"的入口统一走这条路：

1. **Linux syscall**：bionic 的 `svc #0`
2. **JNIEnv 函数表**：表项指向 thunk
3. **导入符号**：GOT 槽指向 thunk（loader 负责填）
4. **RegisterNatives**：本身就是一个 JNIEnv 函数，自动覆盖

`SvcDispatcher` 因此退化成两个分支：`syscall` 和 `host_stub`。不再需要"按 syscall 名写一堆 switch 去拦 JNI"。

### 2.3 返回路径

- 整数返回值写 x0；浮点写 d0/s0（按签名决定）
- PC 处理见 §3
- thunk 最后的 `ret` 把控制权交回 guest 调用方

**ABI 只适配一次**：JNI 的 `JNIEnv*` 在 x0、`jobject` 在 x1，其余按类型规则；这和普通 C 调用一致。`abi_adapter` 负责"按签名读寄存器/写返回值"，不负责语义。

### 2.4 为什么不是别的做法

- **加载真实 libc.so**：需要完整内核（mmap 语义、信号、VDSO、动态链接器），是另一个项目
- **每个符号写一个 switch**：不可维护，且 JNI 函数表是运行期才可见的
- **hook 某条已知指令**：只对特定库有效，不通用

只有"统一 trap"这一条路能同时覆盖 syscall、JNI、导入符号。

## 3. 阻塞 syscall 的完成语义（不重入）

### 3.1 结论

阻塞的 syscall **不重放、不回退 PC**。handler 第一次进入时就把事做完（登记等待队列、记下缓冲区、记下死线），挂一个 `PendingSyscall` 到线程上，然后挂起；被唤醒/超时/信号时调 `complete(reason)` 算出 x0，清掉它，从 `svc+4` 继续。

**线程会挂起，但同一个 svc 永远只进 handler 一次。**

> **待实测**：本节是设计结论。Unicorn 侧的机制（hook 内 `uc_emu_stop()` 后 PC 是否稳定在 `svc+4`、回宿主写 x0 再 `uc_emu_start` 能否续跑）由 M0 探针 3/4 确认。
> 若实测不符，退路是 §3.6 的显式重放，改动只限 SVC dispatcher，不影响线程模型与内存模型。

这条推翻了早期的"`PC -= 4` 重入"方案。重入的四个实际问题：

1. **副作用做两次**：阻塞 `read` 若第一次已拷了部分数据，重入会在偏移 0 再拷一遍
2. **计时从头来**：`nanosleep` 重入按完整时长重睡，而不是剩余时间
3. **语义偏差**：内核的 `FUTEX_WAIT` 返回后不再检查值；重入的二次检查会多返回 `EAGAIN`
4. **trace 重复**：同一个 syscall 在日志里出现两次，分析时容易误判

### 3.2 源码事实（决定"非阻塞路径什么都不用做"）

AArch64 的 SVC 在触发异常前，**PC 已经被设成 `svc + 4`**：

- `qemu/target/arm/translate-a64.c:14514`：`s->base.pc_next += 4;`
- `qemu/target/arm/translate-a64.c:2051`：`gen_exception_insn(s, s->base.pc_next, EXCP_SWI, ...)`
- `qemu/target/arm/translate-a64.c:281-287`：`gen_exception_insn` 先 `gen_a64_set_pc_im(pc)` 再 `gen_exception`
- `qemu/accel/tcg/cpu-exec.c` 里对 x86/mips/riscv/sparc 有 `+= 4` 的补偿，**AArch64 没有**——因为翻译器已经做了
- intno：`EXCP_SWI = 2`（`qemu/target/arm/cpu.h:33`），hook 里用它区分异常类型

所以 `UC_HOOK_INTR` 回调里读到的 PC 就是"下一条指令"。**正常返回、阻塞挂起两条路径都不需要动 PC。**

### 3.3 规则

| 情况 | 处理 |
|---|---|
| 非阻塞（普通 syscall、futex 值不匹配、host stub） | 写 x0（/d0），**PC 不动**，hook 返回 |
| 阻塞（futex_wait、阻塞 read、nanosleep、join） | 生成 `PendingSyscall` 挂到线程；标 Blocked；`uc_emu_stop()`；**PC 不动** |
| 唤醒 / 超时 / 信号 | `op->complete(reason)` 得 x0，清 pending，标 Runnable，从 PC（`svc+4`）继续 |
| 预占（watchdog / 时间片） | 不生成 pending；标 Preempted；恢复后原地继续 |

### 3.4 PendingSyscall

```cpp
struct PendingSyscall {
    virtual ~PendingSyscall() = default;
    // 返回要写进 x0 的值（负数为 -errno）。
    // nullopt = 条件仍不满足（虚假唤醒），继续睡。
    // 只有这里可以产生阻塞 syscall 的副作用。
    virtual std::optional<int64_t> complete(WakeReason reason) = 0;
};
```

- 创建于 handler 决定阻塞的那一刻，存进 `RuntimeThread::pending`
- 一个线程同一时刻最多一个
- `WakeReason`：`FutexWoke`、`TimerExpired`、`Signal`、`ThreadExited`（`-ESRCH`）
- 线程被销毁时直接丢弃，不 complete
- **阻塞 ≠ 预占**：前者恢复时要写 x0、有 pending；后者原地继续、没有 pending。`RunResult`/`ThreadState` 要分开建模

### 3.5 例子

```asm
0x1000: mov x8, #98      ; SYS_futex
0x1004: svc #0
0x1008: cbz x0, done
```

- 进入 hook：PC = `0x1008`，x8 = 98
- futex 值不匹配 → x0 = `-EAGAIN`，返回 → guest 从 `0x1008` 继续
- 需要睡下 → 创建 `FutexWaitOp`（记录 uaddr、val），登记等待队列，标 Blocked，`uc_emu_stop()`
- `FUTEX_WAKE` → `complete(FutexWoke)` 返回 0 → 写 x0 → 从 `0x1008` 继续
- 信号 → `complete(Signal)` 返回 `-EINTR` → 从 `0x1008` 继续
- 超时 → `complete(TimerExpired)` 返回 `-ETIMEDOUT` → 从 `0x1008` 继续

### 3.6 EINTR / 重启

v1 不做 `SA_RESTART`：信号一律返回 `-EINTR`，交给 bionic/pthread 的调用方自己重试（它们本来就处理 EINTR）。

将来若必须实现 `SA_RESTART`：`PendingSyscall` 里额外保存 svc 地址，信号到达时选择"丢弃 pending + 把 PC 设回 svc"再恢复，走一次**显式**重放。这是例外路径，不是默认路径。

### 3.7 v1 的阻塞面

只需要两个：`futex`、`clock_nanosleep`。VFS 是同步宿主 I/O，普通文件 `read/write` 不会阻塞；管道/socket 在 v1 不实现。其余 syscall 一律同步完成。

## 4. 线程模型

### 4.1 真正的问题

`uc_emu_start()` 是同步调用。如果多个 guest 线程共用一个 `uc_engine`，那么：

- T1 在 futex 上睡下时，它的宿主线程仍然**停在 `uc_emu_start` 里面**
- 只要 T1 不返回，engine 就不能被 T2 使用
- 结果：一个线程阻塞，整个实例停摆

这不是"上下文切换慢"的问题，是"阻塞的线程占着引擎"的问题。

### 4.2 对外部评审意见的修正

评审意见推荐"每个 RuntimeThread 一个宿主线程"（方案 B），方向正确，但有两处要改：

1. **"同一个 `uc_engine*` 不能嵌套 `uc_emu_start`"是错的**
   - `include/uc_priv.h:17`：`UC_MAX_NESTED_LEVEL = 64`
   - `uc.c:1096`：`nested_level` 检查
   - `uc_priv.h:417`：`sigjmp_buf jmp_bufs[UC_MAX_NESTED_LEVEL]; // To support nested uc_emu_start`
   - 因此 host→guest 回调直接在同一 engine 上嵌套 `uc_emu_start` 即可，**不要为每层嵌套创建新 engine**
2. **真正需要的是"每个 RuntimeThread 一个 `uc_engine`"**，而不是每个实例一个
   - 阻塞的线程要能保留自己 engine 的执行状态（嵌套层数、jmp_buf、已翻译块），同时把 CPU 让给别人
   - 共用 engine 时，暂停中的线程会让 engine 的嵌套状态无法被他线程安全使用

### 4.3 最终模型 B'：每线程 engine + 实例级大锁

```text
RuntimeInstance (host 对象)
├── MemoryManager ────────── 宿主后备唯一权威（mmap）
│     ├── region A: guest 0x0..     ← host ptr P_A
│     └── region B: ...             ← host ptr P_B
│            ▲ uc_mem_map_ptr(P_A)      ▲ uc_mem_map_ptr(P_A)
├── RuntimeThread 0 ── 宿主线程 0 ── uc_engine E0 ── 自己的 TB cache
├── RuntimeThread 1 ── 宿主线程 1 ── uc_engine E1 ── 自己的 TB cache
├── ...
└── GuestExecutionLock（实例级，同一时刻只允许一个 engine 执行 guest 代码）
```

**三条不变量**：

1. **1:1:1**：guest 线程 = 宿主线程 = `uc_engine`
2. **地址空间视图一致**：任何 map/unmap/protect 都要 replay 到所有 engine；新建 engine 要重放全部已有 region
3. **同一时刻只有一个 engine 在执行 guest 代码**；线程阻塞时释放大锁

### 4.4 为什么还要大锁（不真并行）

guest 的原子指令在多个 engine 真并发时会坏：

- `LDXR/STXR` 的 exclusive monitor 是**每个 engine 一份**；两个 engine 真并发时，STXR 可能在不该成功的时候成功
- LSE 原子（`ldadd/cas`）跨 engine 的宿主内存操作不保证原子
- 结果：guest 的 pthread mutex、引用计数可能坏

串行化后，guest 线程之间不会真并发，语义就对了。签名场景单实例不需要并行；unidbg 也是串行化模型。

宿主线程在等大锁时是**在 `uc_emu_start` 之外**等，所以不会占着 engine。线程阻塞在 futex 上时，先释放大锁再睡。

### 4.5 副作用与实现要点

- **`uc_context_save/restore` 不再需要**：engine 就是该线程的寄存器组。`RuntimeThread` 只需要 `{engine, host thread, guest stack, tls_tp, state, wait queue}`；设计文档里 `regs[31]` 这个字段可以删
- **内存共享**：`uc_mem_map_ptr`（`unicorn.h:1166`）。它把宿主内存映射进 engine，Unicorn 不拥有它：
  - `qemu/softmmu/memory.c:65` `memory_map_ptr` → `memory_region_init_ram_ptr`，只记 `ram->perms`，**不会 mprotect 宿主内存**
  - `qemu/exec.c:1131` 带 `RAM_PREALLOC` 标记，`uc_mem_unmap` **不会 free** 你的指针
  - 因此多 engine 共享同一块内存、各自权限不同是安全的；guest 的 mprotect 只影响模拟语义
- **数据一致性免费**：TCG 的 RAM 访问直接落到宿主内存，数据写入对其他 engine 立即可见；只有**权限**和**代码翻译**需要广播
- **hook / trace 要广播**：注册到所有 engine（包括后来创建的）
- **SMC 失效要广播**：`uc_ctl(UC_CTL_TB_REMOVE_CACHE)` 对所有 engine 逐一调用（`unicorn.h:589`）
- **guest 自己写代码页**：W+X 区要加 `UC_HOOK_MEM_WRITE`，否则解壳/JIT 场景会执行到旧 TB
- **`callFunction`**：投递到主 RuntimeThread 并等待完成（condvar），不要从任意宿主线程直接碰 engine
- **watchdog/timeout**：`timeout` 参数每次调用会创建一个宿主线程（`uc.c:1036-1040`），而 `count` 是每指令 hook（`uc.c:1043`）。生产路径应该用"实例 watchdog 线程 + 跨线程 `uc_emu_stop`"，其安全性进 M0 探针

### 4.6 不采用 fiber 的理由

fiber 只省栈内存（几十 KB vs 线程 1MB 虚拟栈），但：

- 仍然需要每 fiber 一个 engine（原因同 §4.2）
- 暂停点必须发生在 SVC hook 里，swapcontext 的调用链比 condvar 复杂
- gdb 看线程栈比看 fiber 栈直观

签名场景的 guest 线程数是个位数到几十，线程开销可接受。fiber 留作以后优化，接口不变。

### 4.7 对主设计文档的影响

| 主文档位置 | 需要的修改 |
|---|---|
| 公理"Guest 是宿主上的特权协程" | **改为"Guest 是宿主上的特权线程"**：每个 guest 线程 = 一个宿主线程 + 一个 engine；guest 内存由 Memory 持有，所有 engine 共享 |
| §4.3 两级调度 / HostThreadPool / RunnableQueue | **删除**；调度单位是宿主线程本身 |
| §5.2 `RuntimeThread` 结构 | 删掉 `regs[31]/pc/sp`，改为持有 engine |
| §6.1 "Backend 归 RuntimeInstance" | 保留；但一个 Backend 内部管理 N 个 engine，`invalidate_code()` / `add_hook()` 广播 |
| §4.4 MemoryPool | **变成可行**：Memory 的宿主后备就是 pool；用 `uc_mem_map_ptr` 映射到各 engine |
| §6.2 ExecutionBudget | 保留，但定位从"协作调度"变成"watchdog/超时"；`instruction_count` 只用于分析模式 |

## 5. M0 探针清单（九条，全部要有实测数据）

1. `svc #0` → `UC_HOOK_INTR`，intno == 2
2. hook 里 PC 是否等于 `svc+4`（本文件 §3.2 的结论）
3. 不碰 PC + 写 x0，guest 能从下一条继续
4. 挂起式：hook 里 `uc_emu_stop()`，PC 保持 `svc+4`；回到宿主后 `uc_reg_write(x0)`，再次 `uc_emu_start` 从 `svc+4` 继续，寄存器/内存状态保持
5. `mrs x0, tpidr_el0` 读到 host 写入的 `UC_ARM64_REG_TPIDR_EL0`
6. 同一 engine 嵌套 `uc_emu_start`（host→guest 回调）可用，层数上限
7. 两个 engine 在两条宿主线程里同时执行；`uc_mem_map_ptr` 共享内存；数据互相可见
8. `uc_mem_map_ptr` + `uc_mem_protect` 的行为：guest mprotect 不影响宿主映射；不同 engine 权限可不同
9. 跨线程 `uc_emu_stop`（watchdog）与对暂停中 engine 做 map/protect/`uc_ctl` 是否安全
